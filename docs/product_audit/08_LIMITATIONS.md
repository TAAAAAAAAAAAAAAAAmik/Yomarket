# 08. Ограничения продукта

Реальные границы: что продукт не умеет, где он зависит от чужих систем и где
может сработать не так. Собрано по коду и по живым отказам, зафиксированным в
проекте.

Раздел нужен трём читателям: поддержке (чтобы отвечать), маркетингу (чтобы не
обещать), продакту (чтобы планировать).

---

## 1. Чего нет в Integration API Юмаркета — и потому нет в боте через API

| Чего нет | Следствие |
|---|---|
| Изменение цены | **бот не умеет менять цену вообще.** У товара в панели тоже нет такого поля. Экран цен — только просмотр |
| Поднятие объявлений | идёт через панель продавца; нужна живая сессия панели |
| Вывод средств | то же самое |
| Отзывы | то же самое |

Методы `bump_ad`, `bump_all_ads`, `withdraw_balance`, `get_reviews` были
удалены из клиента намеренно. `bot/tests/test_dead_buttons.py` падает, если
они вернутся.

## 2. Поведение маркетплейса, которое нельзя обойти

| Поведение | Что это значит |
|---|---|
| **В закрытый заказ писать нельзя** (`no_active_orders_in_chat`) | ни боту, ни человеку. Совет «ответьте вручную» туда — обещание невозможного, и бот его не даёт |
| **Статус `unpublish` через API не публикуется** | маркетплейс принимает запрос (HTTP 200), статус не меняет. Такие товары публикуются только на сайте |
| **`accepted` ≠ «положил»** | ответ `{"status":"ok","accepted":N}` означает «взял в работу». Позиции появляются с задержкой |
| **Цена приходит объектом**, не числом | `{"amount":129,"base_amount":129,"currency":"RUB"}`; как скаляр превращается в ноль |
| **Списки отдаются курсором** | первая страница — это не «все». Курсор лежит в `links.next_cursor`, и `meta.has_more: false` — стоп даже при непустом курсоре |
| **Справочник разделов больше четырёх тысяч записей** | целиком не вычитывается; имена спрашиваются поимённо и запоминаются |
| **Списка чатов в API нет вовсе** | чаты вне заказов добавляются руками (`/watch_chat`) |
| **Позиции товара в выдаче в API нет** | читается с публичной витрины — зависит от её вёрстки |
| **Действие «в работу» неоднозначно** | на тестовом заказе покупатель сразу увидел «магазин сообщил, что выполнил заказ». Ручная кнопка убрана |

## 3. Лимиты запросов

### Юмаркет — **не опубликованы нигде**
Сколько запросов в минуту разрешено, неизвестно. Поэтому темп не угадывается,
а нащупывается: опрос чатов отступает вдвое на `too_many_requests` (до 120 с)
и понемногу возвращается. Замедление показывается продавцу, а не скрывается.

Практические следствия:
* «горячий» чат читается раз в 10 секунд **в лучшем случае**;
* полный обход 25 чатов — раз в минуту;
* при замедлении интервал вырастает до двух минут.

**Proof:** `bot/tasks/manager.py:519`–`:563`.

### AppRoute — опубликованы (`GET /api/v1/rate-limits`)
| Вызов | Лимит в минуту |
|---|---|
| `GET /services` (каталог целиком) | **2** |
| `GET /orders` | 2 |
| `GET /orders` с фильтром | 20 |
| `GET /orders` с `unhide=true` | 5 (отдельный счётчик) |
| `POST /orders` (покупка) | 120 |
| `GET /services/{id}/items/{id}` | 120 |

Из-за лимита на каталог он кешируется на пару минут: он отдаётся одним ответом
на 1263 услуги, и два оплаченных заказа подряд означали бы два тяжёлых чтения
по 90 секунд таймаута, всё это время держа опрос заказов.

### Telegram
| Ограничение | Следствие |
|---|---|
| Сообщение — 4096 символов | длинные экраны обрезаются (`ui.LIMIT = 3900`, `ui.clip`) |
| `callback_data` — 64 байта | курсор этого маркетплейса (70+ символов base64) **в кнопку не влезает**. Курсоры держатся в памяти процесса, в кнопку едет номер |
| Сообщение старше двух суток править нельзя | с заявки на оплату тогда хотя бы снимаются кнопки |
| Боту нельзя писать первым | продавец, не нажавший `/start` у нового бота, недостижим |

**Существенное следствие лимита `callback_data`:** номера страниц живут в
памяти процесса (`handlers/pager.py`, `_KEEP = 30` на сущность). После
перезапуска бота кнопка «Следующая →» из старого сообщения отвечает «список
устарел» — а не открывает первую страницу под видом следующей.

## 4. Зависимость от сессии панели продавца

Без живой сессии панели **не работают**:
создание товара · поднятие (любое) · вывод средств · отзывы · журнал
операций (то есть статистика из панели) · список товаров панели · удаление и
скрытие товаров.

Куки истекают **молча**. Бот проверяет здоровье сессии раз в 30 минут, чтобы
продавец не узнавал об этом посреди работы.

Отдельно: у товара в панели **три источника данных**, и Nova разрешает их
независимо. 403 на форме правки при живой карточке — обычное дело; закрытая
форма не отменяет чтение товара.

**Proof:** `bot/automation/panel.py:3911`, `bot/tasks/manager.py:4731`.

## 5. Зависимость от поставщика (автовыдача)

| Ограничение | Что значит |
|---|---|
| **Ключ и деньги — продавца** | продукт не покупает коды за свой счёт |
| **Белый список IP** | бот живёт там, где адрес меняется при каждом выкате. «Ключ не сработал» после деплоя означает обычно именно это |
| **Лечится прокси с постоянным адресом** | в белый список вписывается прокси. Через него обязаны идти и рабочие вызовы, и диагностика |
| **Право `orders:write`** | это не «запись», а выдача кодов: без него ключ покупает, но кода не отдаёт. Деньги списаны, выдать нечего |
| **Два вида ключа** | временный на 48 часов и постоянный; белый список нужен постоянному |
| **HTTP 200 ничего не значит** | результат лежит в `statusCode` внутри тела |
| **`IDEMPOTENCY_REPLAY` — это успех** | «такой заказ уже был, отдаю прежний результат». Принять за отказ значит купить второй раз |
| **`IN_PROGRESS` с пустым результатом** | заказ создан, кода ещё нет — нужен опрос |
| **Ожидание кода ограничено 120 с** | оно занимает поток, а замок общий с опросом чатов. Недоведённое подбирается позже |
| **Для Roblox нет прямого пополнения** | только коды (`voucher`), 26 услуг, `fields: null` |

## 6. Тарифные и доступные ограничения

| Ограничение | Подробности |
|---|---|
| **Копия товара и залив — только администраторам** | `features.ad_templates_shown` = `is_admin`. Заслон стоит на списке и на каждом нажатии, а не только на кнопке |
| **AutoStars скрыт целиком** | `features.STARS_HIDDEN = True`: кнопка, команды, диагностика, строка приветствия, прокси и фоновая выдача — всё разом |
| **Пробы не выдаются поверх оплаченной подписки** | `paid_now`; отказ называет свою причину |
| **Заявка на оплату — одна в час на человека** | `PAID_CLAIM_EVERY = 3600` |
| **Пока «Требовать подписку» выключено, бот бесплатен для всех** | это решение владельца, а не свойство продукта |
| **Данные удаляются через 3 дня после конца подписки** | обещано в политике конфиденциальности |

## 7. Ограничения автоматизаций

| Автоматизация | Потолок |
|---|---|
| Автовосстановление | не больше **40** товаров за проход; остаток показывается как очередь |
| Догон «зависшей» работы | не больше **3** заказов за проход |
| Залив | не больше **5** товаров за проход, очередь круговая |
| Автовозврат | **3** возврата в сутки, по умолчанию выключен |
| Поднятие по позиции | пауза 6 ч на товар, 3 поднятия в сутки, бюджет в ₽ |
| Журнал залива | 30 записей; список созданного — 3000 |
| Журнал автоответов | 30 записей; состояние по чатам — 200 |
| Остатки | до 200 строк в списке |
| Память ответов копии | 60 образцов |

## 8. Ограничения хранилища

| Режим | Что значит |
|---|---|
| **PostgreSQL** (`DATABASE_URL` задан) | штатный режим |
| **JSON-файлы** (переменной нет) | на платформах вроде Railway **стираются при каждом редеплое**. `/version` это показывает (`ephemeral_disk`) |
| **Ключ шифрования не задан** | seed-фраза хранится **как раньше**, без шифрования, и бот говорит об этом прямо, а не делает вид. Подстраховки «выведем ключ из того, что рядом» нет намеренно — это не шифрование |

## 9. Технические edge cases и режимы отказа

| Случай | Что происходит |
|---|---|
| **Два бота с одним токеном** | Telegram отдаёт обновления одному потребителю: часть сообщений теряется. Снаружи — «отвечает через раз» |
| **Вебхук на токене** | Telegram **не отдаёт обновления опросом вообще**, а отправка работает: уведомления приходят, на команды бот не отвечает. Снимается при запуске (`clear_webhook`), не выбрасывая накопленные обновления |
| **Обе причины приходят как 409 Conflict** | лечатся противоположно, и бот не выбирает наугад: если текст Telegram не называет причину, он так и пишет — «причины две» |
| **Одна неудачная попытка опроса** | это **не** «бот не получает сообщения». Тревога только по стойкому молчанию: попытки не удаются дольше 90 с И за это время не пришло ни одного обновления |
| **Смена токена бота** | продавцы остаются в переписке со старым ботом, а новому Telegram запрещает писать первым, пока человек не нажал `/start` |
| **Продавец заблокировал бота** | постоянная недостижимость отличается от сетевого сбоя; владельцу сообщается один раз на продавца |
| **Текст с маркетплейса с символом `<`** | любой текст (название магазина, товара, письмо покупателя) экранируется перед вставкой в HTML — иначе одиночный `<` роняет всю отправку |
| **Процесс убит во время записи в файл** | запись атомарна (`.tmp` + `os.replace` + `fsync`). Прежний способ оставлял обрезанный JSON, и продавец терял токен, правила и цены разом |

## 10. Что нельзя проверить и потому нельзя обещать

| Не проверено | Почему это важно |
|---|---|
| Реакция маркетплейса на минутный залив | ~1440 объявлений в сутки на товар; возможен ответ ограничением |
| Принимают ли оба домена поставщика один ключ | API совпадает побайтно, но про кабинеты это ничего не говорит |
| Правка цены через API | не проверялась ни разу; правка, которая может не примениться, хуже её отсутствия |
| Точная семантика `POST /orders/{id}/work` | на тестовом заказе покупатель увидел «магазин выполнил заказ» |
| Лимиты запросов Юмаркета | нигде не опубликованы |
