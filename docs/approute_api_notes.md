# AppRoute Public API — разбор под автовыдачу гифт-карт

Изучено 16.08 по официальному SDK и OpenAPI:
`github.com/AppRoute-FZCO/AppRoute-Public-API-SDK`. Это заметки по чужому
API, не наш код. Проверено чтением исходников SDK, не догадками; но **ни
один вызов вживую не сделан** — ключа у нас нет.

**17.08: поставщик выбран — AppRoute.** Написан клиент только на чтение
(`bot/automation/approute.py`) и экран доступа (`bot/handlers/approute.py`):
`/apr_login`, `/apr_balance`, `/apr_stock`. Покупки нет ни одной — сначала
живой каталог, потом выдача.

**Тогда же перечитан транспорт SDK, и две записи ниже пришлось поправить:
на проводе camelCase, а «получилось ли» решает поле `code` в теле, а не
статус HTTP.** Обе поправки отмечены на месте.

Сравнивается с ns.gifts, клиент к которому уже написан
(`bot/automation/nsgifts.py`, документация — `docs/ns_api_reference.md`).

---

## Коротко: да, легче. Заметно.

| | ns.gifts | AppRoute |
|---|---|---|
| авторизация | HMAC-подпись, токен на 2 ч, защита от повтора | один заголовок `X-API-Key` |
| клиент | пишем сами (~200 строк одной подписи) | официальный SDK, есть и REST напрямую |
| выдача кода | `create_order` → `pay_order` → `order_info` | коды приходят **в ответе на создание** |
| повтор после обрыва | `custom_id`, 409 на повторную оплату | тот же `reference` → код `IDEMPOTENCY_REPLAY` и прежний результат |
| отказы | коды HTTP, разбираем сами | типизированные: нет в наличии, не хватает денег, лимит |
| сухой прогон | нет | `checkOnly` для пополнений (DTU) |

Главное различие не в удобстве, а в числе шагов, на которых можно потерять
деньги: у ns.gifts их два (создали — оплатили), у AppRoute один.

## Как устроено

**База:** `https://approute.io/api/v1` (или `approute.ru/api/v1` для России).
**Ключ:** `X-API-Key`, берётся в кабинете. Больше ничего — ни подписи, ни
времени, ни токена с TTL. Кабинеты раздельные: ключ от `.io` в `.ru` не
работает, поэтому регион у нас переключается кнопкой.

**Конверт — главное, что нужно знать про этот API.** Каждый ответ приходит в
виде

```
{status, code, message, traceId, data, errors[]}
```

и **успехом считаются ровно три кода**: `OK`, `ACCEPTED`,
`IDEMPOTENCY_REPLAY` (так устроен `handle_response` в транспорте SDK).
Остальные — отказ, и приезжают они в том числе с HTTP 200: «нет в наличии»,
«не хватает средств», «лимит». Клиент, который смотрит на статус HTTP, будет
докладывать об успехе там, где ничего не произошло, — то самое, ради чего в
`CLAUDE.md` написано правило 1.

`traceId` есть в каждом ответе: по нему поставщик находит запрос у себя. Мы
печатаем его в каждом отказе.

**`IDEMPOTENCY_REPLAY` — это успех.** «Такой заказ уже был, отдаю прежний
результат». Это и есть готовая защита от двойной покупки после обрыва — она
лучше, чем поиск по `/orders`, который был записан ниже: искать ничего не
надо, достаточно повторить запрос с тем же идентификатором. Принять этот код
за отказ значит купить второй раз.

**На проводе camelCase.** В примерах SDK поля выглядят как `item_id`,
`reference_id`, `client_time`, `check_only` — но это его собственное удобство:
`convert_keys_to_camel` переводит их в `itemId`, `referenceId`, `clientTime`,
`checkOnly` перед отправкой, а ответ переводит обратно в snake_case. **Мы
идём без SDK, значит имена пишем и читаем сами, camelCase.** Ниже они
приведены к тому виду, в котором реально ходят по проводу.

**Повторяет SDK только 429 и 5xx**, уважая заголовок `Retry-After`. Наш
клиент делает то же самое: своя оценка была бы догадкой поверх его ответа.

**Каталог:** `GET /services` → `data.items[]` — товары (`Product`), у каждого
`items[]` — номиналы (`ProductItem`) и `fields[]` — схема полей заказа.
Поля товара: `id`, `name`, `type` (`voucher` | `direct_topup`), `categoryName`,
`subcategoryName`, `countryCode`. Поля номинала: `id` (это и есть `itemId` для
заказа), `name`, `nominal`, `price`, `currency` (только USDT), `available`,
`stock`.

**У ответа есть `hasNext`, но постраничного чтения каталога нет** — ни в SDK
(`services.list()` не принимает ни одного параметра), ни в `openapi.yaml`.
То есть дочитать список нечем, и промолчать об этом нельзя: «Роблокса нет» и
«нам прислали не весь список» — разные ответы. Бот говорит об этом прямо.

Остальные вызовы:

* `GET /services` — список товаров;
* `services.get_item(service_id, item_id)` — конкретный номинал;
* `lookup_items` — пачкой до 100 пар `(service_id, item_id)` за один запрос,
  ответ в том же порядке, у каждой строки `found` и либо `item`, либо
  `error`.

**Заказ:** `POST /orders`

⚠️ **Здесь SDK и `openapi.yaml` расходятся, и до первой покупки это надо
сверить живым вызовом.** SDK (`orders.create`) собирает тело
`ordersType` + `referenceId` + `itemId` + `quantity`; схема `PurchaseRequest`
в `openapi.yaml` требует `clientTime` + `reference` + `itemId` + `quantity`,
про `ordersType` и `referenceId` не знает вовсе и лишние поля запрещает
(`additionalProperties: false`). Сам файл предупреждает, что пути `/orders`
в нём не описаны и источник истины по набору операций — SDK; но схему тела
он при этом описывает. Пока расхождение не снято, выдачу писать нельзя —
ровно так мы потеряли день на Fragment.

```
ordersType: "shop" (коды) | "dtu" (прямое пополнение счёта)
referenceId / reference: наш идентификатор — придумывается ДО вызова
itemId, quantity
fields: [{key, value}]   — для DTU: куда пополнять
checkOnly: true          — сухой прогон, заказ не создаётся
```

**Ответ** (`PurchaseResponse`, внутри `data`):

```
transactionUUID, status, price, currency
result.vouchers[]: {pin, serialNumber, expiration}
result.esim: {matchingId, qrCodeText, smdpAddress, iccid}
result.attributes: {ключ: значение}
```

**`pin` — это и есть код гифт-карты**, он приходит сразу.

**Поиск заказа:** `GET /orders?referenceId=…` → строки с теми же
`vouchers`. То есть обрыв связи после отправки запроса **восстановим**: наш
`reference_id` мы придумали до вызова, по нему и спросим, чем всё кончилось.

**Баланс:** `GET /accounts` → `data.items[]`: `currency` (**только USDT**),
`balance`, `available`, `overdraftLimit`, `recentActivity[]`. Плюс
`GET /accounts/transactions`. У ns.gifts баланс в USD — сравнивая закупку,
сравниваем деньги, а не числа.
**Пополнение:** `/funds/*` — счета, USDT, TON, Bybit UID.

**Отказы** разделены самим API: нет в наличии, не хватает средств, лимит
запросов, конфликт, ошибка вышестоящего поставщика, неверный ключ. Это
ровно то, что нам нужно для правила «каждое „ничего не произошло“
объясняется» — переводить придётся, но различать уже не надо.

## Что это НЕ решает

1. **Есть ли там Roblox — неизвестно.** Тот же вопрос, что и с ns.gifts, и
   ответ тот же: смотреть каталог живым ключом. В SDK и OpenAPI списка
   товаров нет.
2. **Цены неизвестны.** Легче в разработке ≠ выгоднее в закупке. Сравнивать
   надо по конкретному номиналу.
3. **У продавца уже есть кабинет ns.gifts** с балансом. Переход — это новый
   аккаунт, новое пополнение и, возможно, новая проверка документов.
4. **Обрыв на создании заказа остаётся опасным местом.** Ответ с кодами
   можно не получить, хотя заказ создан и деньги списаны. Спасает
   `reference_id`: он придумывается **до** вызова и сохраняется, иначе
   восстановить нечем. Это то же правило, которое мы вывели на звёздах:
   оборванное ожидание — «неизвестно», а не «не вышло», и повторять нельзя.
5. **Зависимости.** Официальный SDK тянет `httpx` и `pydantic>=2`. Второй у
   нас уже есть (через aiogram), первый — новый. При такой простой
   авторизации SDK не обязателен: `requests` + заголовок делают то же самое,
   а зависимостей в этом проекте лучше меньше.

## 17.08, живая проба: чего в документации нет

Первая же попытка проверить ключ на настоящем сервере дала два факта, каждый
из которых в SDK и OpenAPI отсутствует.

**1. Ответ пришёл HTTP 200 с `traceId`, но без поля `code`.** То есть конверт
не той формы, что описан в их же SDK, — а `code` это единственное, по чему
определяется, получилось ли. Бот теперь не выдаёт такой ответ ни за успех, ни
за понятный отказ: он перечисляет, что в теле было, и зовёт `/apr_debug`.
Первая версия печатала «❌ HTTP 200» — цифру, из которой не следует ничего.

**1a. 17.08, вторая проба (`/apr_debug`) — конверт снят целиком.** Все четыре
запроса (`/whoami` и `/accounts`, на обоих доменах) ответили HTTP 200 с
одинаковым телом:

```
{data, errorCode, errors, status, statusCode, statusMessage, traceId}
```

Ни `code`, ни `message` — то есть **это другой конверт, не тот, что в их
SDK**. Соответствие такое:

| SDK | живой ответ |
|---|---|
| `code` | `errorCode` (название отказа) |
| `message` | `statusMessage` (причина словами) |
| — | `statusCode` — числовой код **внутри тела**; снаружи HTTP всегда 200 |
| `status` (enum строкой) | `status` — по имени похоже на флаг |
| `errors`, `data`, `traceId` | те же |

Одинаковая форма на `approute.io` и `approute.ru` означает, что за обоими
доменами один шлюз.

Бот понимает теперь оба конверта. Но важная оговорка: **признак успеха в
живом конверте выведен из имён полей, а не прочитан в документации** — её
для этой формы нет вовсе. Поэтому спорный ответ считается отказом: принять
отказ за успех значит отчитаться о выдаче, которой не было, а обратная
ошибка стоит только лишнего сообщения с `traceId`.

Ещё не выяснено: как выглядит **успешный** ответ. Все снятые до сих пор —
отказы (или неотличимы от них). Значения `status`, `statusCode` и
`statusMessage` при удачном запросе никто не видел.

**1b. Ключей в кабинете два вида, и это меняет разбор.** Со слов продавца:
есть **временный ключ на 48 часов** и **постоянный**, и белый список IP
нужен именно постоянному. Проверить это самим нечем — в SDK и OpenAPI про
временные ключи нет ни слова, — но версия правдоподобная и объясняет отказ
без единой строчки про IP.

Косвенно за неё говорит форма ключа: в README у поставщика примеры вида
`sk_live_…`, а выданный кабинетом — `wli-…`, 43 символа. Разные формы вполне
могут означать разные виды ключей.

Отсюда две правки: отказ `UNAUTHORIZED` называет **три** причины (истёк срок,
белый список, не тот кабинет), а проверка «похож ли на ключ» по виду
`sk_live_` не делается вовсе — она отвергала бы ровно то, что поставщик
выдал.

Что покажет: в новом `/apr_debug` печатается `statusMessage`. Про истёкший
ключ и про запрещённый IP сервер пишет разное, и различить их можно будет
одним взглядом.

**2. У AppRoute белый список IP, и есть `GET /whoami`.** Ни того, ни другого
нет ни в SDK, ни в `openapi.yaml` — это сказано на экране выдачи ключа в
кабинете, там же дана проверочная команда:

```
curl -H "X-API-Key: …" https://approute.io/api/v1/whoami
```

Бот живёт на Railway, где адрес меняется при каждом выкате. Значит «ключ не
сработал» после деплоя чаще всего означает «нас нет в белом списке», и
выясняется это только с самого сервера — команда `/apr_whoami` или кнопка
«🪪 Наш IP у поставщика».

**Попутно: кабинеты, возможно, не разделены так строго, как сказано в
README.** Ключ выдан в `approute.ru`, а проверочная команда там же указывает
на `approute.io`. Утверждать ничего не будем — `/apr_debug` спрашивает оба
адреса и печатает, где ключ приняли.

Проверить это чтением исходников нельзя: домен `approute.io` закрыт сетевой
политикой нашей среды разработки (прокси отвечает 403 на соединение), ровно
как `wholesale.ns.gifts`. Факты печатает только бот на Railway.

## Белый список IP и прокси

**Что это.** Поставщик принимает ключ только с заранее названных адресов.
Верный ключ с чужого адреса отвергается — смысл в том, что украденный ключ
без доступа к вашему серверу бесполезен.

**Обычный прокси подходит**, если у него **постоянный** адрес. В белый список
вписывается адрес прокси, а не сервера. Ротационные и «резидентные» прокси,
меняющие адрес на каждый запрос, не годятся принципиально: вписывать нечего.

**Годится ли конкретный прокси — не вопрос совета.** Кнопка «🧪 Годится ли
он» спрашивает наш адрес три раза подряд и сверяет с адресом без прокси.
Отсюда четыре разных ответа, и каждый значит своё: адрес один — годится, и
вот его вписывать; адрес меняется — ротационный, не годится; адрес совпал с
прямым — **прокси не применяется вовсе** (обычно неверный формат строки или
отвергнутый пароль), и «прокси задан» тут ничего не значит; адреса нет —
прокси не отвечает. Три запроса названы выборкой, а не доказательством:
адрес может меняться раз в час, и окончательно подтвердит только принятый
ключ.

Годятся и `http://`, и `socks5://` (для второго нужен PySocks — он в
`requirements.txt`; если сборка без него, бот скажет об этом прямо, а не
уронит запрос английской ошибкой).

**Ключ прокси-провайдеру не достаётся.** Соединение с AppRoute идёт по HTTPS:
прокси видит только имя хоста в `CONNECT`, а заголовки и тело зашифрованы.

**Адрес узнаётся до того, как ключ заработает.** `/apr_whoami` при отказе
ключа всё равно печатает наш исходящий адрес — спрашивает его у стороннего
сервиса тем же маршрутом. Иначе получался замкнутый круг: чтобы узнать, какой
адрес вписать, нужен работающий ключ.

**Требование ко всему коду модуля:** и рабочие вызовы, и диагностика ходят
через одну сессию (`_session`). Проба, ходящая мимо прокси, показала бы
адрес, с которого поставщик нас вообще не видит, — диагностика, врущая про
собственный маршрут, хуже её отсутствия.

## Что дальше — по шагам

Поставщик выбран, разработка идёт на AppRoute. Но вопрос «у кого дешевле
Robux и есть ли он вообще» остался открытым, и отвечает на него только живой
каталог.

1. **Взять ключ** в кабинете (approute.io/dashboard или approute.ru/dashboard)
   и ввести его: AutoRoblox → «🔑 Поставщик AppRoute», либо `/apr_login`.
   Кабинет выбирается там же кнопкой — ключ от одного в другом не работает.
2. **«🧪 Проверить ключ»** — спрашивает баланс, только читает.
3. **`/apr_stock roblox`** (или «📦 Каталог») — есть ли Roblox, под какими
   `serviceId`/`itemId`, почём за номинал, какие поля требует заказ.
4. **Сравнить с ns.gifts** — `/ns_stock robux`, его экран и каталог никуда
   не делись именно для этого.
5. Только после этого — выдача. И до первой покупки снять расхождение SDK и
   `openapi.yaml` по телу `POST /orders` (см. выше): чем именно поставщик
   считает `reference` и обязателен ли `clientTime`, знает только живой ответ.
   Идентификатор придумывается и сохраняется **до** вызова — иначе оборванный
   ответ нечем восстановить.

Клиент к ns.gifts остаётся в репозитории и под тестами: пока цены не
сравнили, выбрасывать нечего.
