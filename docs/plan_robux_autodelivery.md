# План: довести автовыдачу Robux до рабочего состояния

**Кому:** параллельным сессиям. План написан так, чтобы его можно было взять
и выполнить, не перечитывая заново документацию поставщика: всё, что нужно
знать про API, лежит в `docs/approute_api_reference.md` (снят с официальной
документации 19.08).

**Что уже есть:** выдача написана целиком — подбор номинала, журнал,
намерение до вызова, код до отправки, доведение оборванной выдачи. Ни строчки
из этого переписывать не надо.

**Что не так:** пять мест разошлись с настоящим API. Каждое из пяти — не
падение, а **молчаливая ложь про деньги**: доложить об отказе там, где заказ
создан; купить второй раз; отправить покупателю замазанный код. Ровно тот
класс поломок, ради которого написан `CLAUDE.md`.

**Главное, что изменилось в замысле:** сухого прогона перед покупкой Robux
**не существует** — `checkOnly` разрешён только для DTU, а Robux у AppRoute
это `voucher`, то есть shop. Пункт «сделать сухой прогон с настоящим
`denominationId`, без него выдачу писать нельзя» закрыт не выполнением, а
опровержением. Чем он заменяется — правка 3.

---

## 0. Правила этой работы

1. **Правки 1–5 независимы.** Можно разобрать по сессиям; порядок номеров —
   по убыванию цены ошибки, а не по зависимостям.
2. **Каждая правка идёт со своим тестом, и тест сначала обязан упасть.**
   Порядок: правка → тест → откатить правку → убедиться, что тест падает →
   вернуть. Тест, который не падает при откате, ничего не проверяет.
3. `BOT_VERSION` в `bot/handlers/start.py` — вверх при каждом коммите.
4. Ветка `claude/where-we-left-off-mul8tu`, перед коммитом `git pull --rebase`.
5. Прогон: `cd bot && python -m unittest discover -s tests -p "test_*.py"`,
   трижды, в перемешанном порядке.

## Правка 1. Успех определяется по `statusCode`, а не по угадыванию

**Где:** `bot/automation/approute.py`, `_live_envelope_is_ok` и `_unwrap`.

**Что сейчас.** Успехом считается ответ, у которого `errorCode` пуст,
`errors` пуст, `data` не `None`, а `statusCode` — один из `("200","201","0","")`.
Признак выведен из имён полей, о чём честно написано в докстринге.

**Почему это дорого.** `statusCode` — числовой enum, и в нём **три** кода
успеха:

* `1` = `ACCEPTED` — «заказ принят в работу» (приходит с HTTP 202). Сейчас
  читается как отказ: деньги ушли, бот доложил, что покупки не было.
* `2` = `IDEMPOTENCY_REPLAY` — «такой `referenceId` уже был, отдаю прежний
  результат». Сейчас читается как отказ. Это и есть **вторая покупка** после
  обрыва — то, от чего вся защита и строилась.

**Как чинить.** Завести enum и решать по нему:

```python
# statusCode — числовой код В ТЕЛЕ ответа; HTTP снаружи почти всегда 200.
# Значения взяты из бандла документации поставщика (см. approute_api_reference §2).
AR_STATUS_CODES = {
    0: "OK", 1: "ACCEPTED", 2: "IDEMPOTENCY_REPLAY", 3: "VALIDATION_ERROR",
    4: "UNAUTHORIZED", 5: "FORBIDDEN", 6: "NOT_FOUND", 8: "LIMIT_REACHED",
    9: "OUT_OF_STOCK", 10: "INSUFFICIENT_FUNDS", 11: "UPSTREAM_ERROR",
}
AR_SUCCESS_CODES = (0, 1, 2)      # OK, ACCEPTED, IDEMPOTENCY_REPLAY


def _status_code(body: dict):
    """Числовой код конверта или None, если его нет вовсе."""
    raw = body.get("statusCode")
    if isinstance(raw, bool) or raw is None:
        return None
    try:
        return int(raw)
    except (TypeError, ValueError):
        return None
```

и в `_unwrap`:

```python
code = _status_code(body)
if code is not None:
    if code in AR_SUCCESS_CODES:
        return body.get("data"), body        # см. правку 4 про второй элемент
    name = AR_STATUS_CODES.get(code, "")
    said = str(body.get("statusMessage") or "").strip()
    raise ARError(name or str(code), explain_code(name, said),
                  r.status_code, str(body.get("traceId") or ""),
                  body.get("errors") or [])
```

Тонкости, которые легко потерять:

* **`data` может быть `null` при успехе** — у HTTP 202 (`ACCEPTED`) поле
  `result` внутри `data` пустое, а у некоторых ответов пусто и само `data`.
  Нынешнее требование «`data is not None`, иначе отказ» надо снять: решает
  `statusCode`. Пустой ответ на покупку разбирается на уровне выдачи (нет
  кодов → это не выдача), а не здесь.
* **Ветку `{code, message}` из SDK можно оставить**, но она проверяется
  **после** `statusCode`, а не до: живой конверт главнее.
* `_looks_like_live_envelope` больше не нужен как развилка — конверт один.
  Удалять его не обязательно, но полагаться на него нельзя.
* Проверка `status` строкой (`"error"`, `"fail"`…) — выдумка, таких значений
  у поставщика нет. Настоящие четыре: `SUCCESS`, `IN_PROGRESS`,
  `PARTIALLY_COMPLETED`, `CANCELLED`.

**Тест** (`bot/tests/test_approute.py`):

* `test_an_accepted_order_is_not_reported_as_a_refusal` — конверт
  `{"status":"IN_PROGRESS","statusCode":1,"data":{"orderId":"o1","result":None}}`
  → разбор считает успехом.
* `test_an_idempotency_replay_is_a_success_not_a_second_purchase` — конверт
  со `statusCode: 2` и кодом внутри → успех, код прочитан.
* `test_a_refusal_names_the_reason_in_russian` — `statusCode: 9` → отказ, в
  тексте «нет в наличии», `traceId` на месте.

Проверить, что тесты падают до правки: первые два обязаны.

## Правка 2. Поле называется `referenceId`

**Где:** `bot/automation/approute.py`, `live_order_body`.

**Что сейчас.** Ссылка кладётся наверх под именем `reference`.

**Почему это дорого.** Такого поля в схеме запроса **нет**. `reference` — это
поле *ответа* `GET /orders` (эхо нашего значения). Поставщик наш `reference`
не видит, значит идемпотентности нет: повтор после обрыва — вторая покупка.
Прежняя запись в `CLAUDE.md` («из двух имён берётся `reference`, потому что
оно возвращается в строке заказа») перепутала запрос с ответом.

**Как чинить.**

```python
def live_order_body(denomination_id: str, quantity: int = 1,
                    reference: str = "") -> dict:
    body = {
        "ordersType": "shop",
        "orders": [{"denominationId": str(denomination_id or ""),
                    "quantity": int(quantity or 1)}],
    }
    if reference:
        # 1..40 символов, уникален в пределах нашего кабинета. Повтор с тем
        # же значением возвращает первый результат и statusCode=2.
        body["referenceId"] = str(reference)[:40]
    return body
```

Заодно: параметр `check_only` из сигнатуры уходит (правка 3).

**Про длину.** `robux.order_reference` собирает `yoo-{номер}-{robux}` — для
номеров вида `1218314` это 20 символов, но обрезание должно быть явным:
ссылка длиннее 40 символов — отказ по схеме на первой же покупке. Обрезать
надо **одинаково при покупке и при поиске**, иначе заказ не найдётся.

**Тест** (`bot/tests/test_approute.py`):

* `test_the_order_reference_goes_into_the_field_the_provider_reads` — в теле
  есть `referenceId` и нет `reference`.
* `test_a_reference_longer_than_forty_chars_is_cut_the_same_way_everywhere` —
  длинная ссылка обрезается одинаково в теле заказа и в параметрах поиска.

## Правка 3. Убрать сухой прогон, поставить на его место проверку номинала

**Где:** `bot/automation/approute.py` (`dry_run_check_sync`, `order_sync`),
`bot/tasks/manager.py` (`_maybe_deliver_robux`, `_robux_finish`, `dry_first`),
`bot/handlers/approute.py` (`/apr_dry_check`).

**Что сейчас.** Перед каждой покупкой уходит `order_sync(..., check_only=True)`,
и покупка не делается, если прогон отказал. На это опирается и доведение
оборванной выдачи (`dry_first`).

**Почему это неверно.** `checkOnly` разрешён **только** для `ordersType=dtu`.
Robux — `voucher`, то есть shop. Что сервер делает с `checkOnly` в теле shop —
неизвестно, и оба исхода плохи: либо отказ по схеме на каждой покупке, либо
поле игнорируется и «сухой прогон» **и есть покупка** — то есть мы покупаем
дважды подряд.

**Чем заменить.** Тем, что документация прямо предлагает для этого случая, —
чтением одного номинала перед покупкой:

```python
def item_sync(creds: dict, service_id: str, item_id: str) -> tuple[bool, object]:
    """Свежие цена и остаток одного номинала.

    Ответ побайтно совпадает с элементом `items[]` в каталоге, но стоит
    один дешёвый запрос (120/мин против 2/мин у полного каталога).
    Это замена сухому прогону: он для shop не разрешён.
    """
    return _guarded(lambda: _client(creds).call(
        "GET", f"/services/{service_id}/items/{item_id}") or {})
```

Перед покупкой:

1. `item_sync(creds, row["service_id"], row["denomination_id"])`;
2. `inStock <= 0` → честный отказ, денег не потрачено;
3. цена изменилась больше чем на заданный продавцом порог — отказ с
   названной причиной (порог можно не вводить сейчас, но цену из ответа
   записать в журнал **до** покупки: потом «почему списалось столько» будет
   нечем объяснить).

`service_id` в строке каталога уже есть — `robux.denominations` его кладёт,
менять там нечего.

**Что делать с существующим:**

* `dry_run_check_sync` — **удалить**. Она отвечала на вопрос «сухой ли наш
  сухой прогон», у которого больше нет предмета.
* `/apr_dry_check` — переписать в `/apr_item <denominationId>`: печатает
  цену, остаток, `isLongOrder`, `minQtyToLongOrder`. Это и диагностика, и
  проверка прав ключа на чтение.
* `/apr_order_probe` — оставить как есть. Он бьёт заведомо несуществующим
  номиналом и денег не тратит; после правки 2 он же покажет, принимает ли
  сервер `referenceId`.
* В `_robux_finish` параметр `dry_first` и вся ветка под ним — убрать.
  Состояние `"собираемся покупать"` при этом остаётся (см. правку 5).

**Тест** (`bot/tests/test_robux_delivery.py`):

* `test_a_purchase_is_not_attempted_when_the_nominal_is_out_of_stock` —
  подделка `item_sync` отдаёт `inStock: 0`, покупка **не вызвана** ни разу.
* `test_the_shop_order_body_carries_no_check_only_field` — в теле нет
  `checkOnly`.

Второй тест звучит мелко, но он единственный, кто не даст вернуть сухой
прогон обратно «по памяти».

## Правка 4. `IN_PROGRESS` доводится опросом

**Где:** `bot/automation/approute.py` (новая функция), `bot/tasks/manager.py`
(`_robux_finish`).

**Что сейчас.** Ответ на покупку разбирается один раз: есть коды — выдаём,
нет — «ответ без кода, посмотрите кабинет».

**Почему этого мало.** Покупка законно отвечает **HTTP 202 / `IN_PROGRESS` /
`result: null`**: заказ принят, код будет позже. Для «долгих» номиналов
(`isLongOrder`) это обычное дело. Сейчас такой ответ либо станет отказом
(до правки 1), либо «ответом без кода» — а код тем временем существует и
оплачен.

**Как чинить.** Две функции с фактами в dict, без прозы:

```python
def order_place_sync(creds: dict, denomination_id: str, quantity: int = 1,
                     reference: str = "") -> dict:
    """Купить. Возвращает факты, а не текст.

    {"ok": bool, "why": str, "status": str, "status_code": int|None,
     "order_id": str, "codes": [str], "replay": bool, "trace_id": str}
    """


def order_codes_sync(creds: dict, reference: str) -> dict:
    """Чем кончился заказ с этой ссылкой — и коды, если они уже есть.

    Ходит в `GET /orders?referenceId=…&unhide=true` (см. правку 5).
    {"ok", "why", "found": bool, "status": str, "codes": [str], "masked": bool}
    """
```

Опрос в `_robux_finish` после `status == "IN_PROGRESS"`:

* первый запрос через 2 секунды, дальше 5, 10, 20, 30, 30… — **но не чаще
  раза в 12 секунд**: у `unhide=true` лимит 5/мин на весь кабинет;
* остановка на терминальном статусе: `SUCCESS`, `PARTIALLY_COMPLETED`,
  `CANCELLED`;
* потолок ожидания — 10 минут; дальше запись остаётся в состоянии
  `"куплен, ждём код"`, и её доводит `_robux_resume` на следующем проходе.
  **Нельзя** оставлять поток занятым дольше: он держит опрос заказов этого
  продавца (это уже записано в `HANDOFF.md` как известная беда).
* `PARTIALLY_COMPLETED` — терминальный. Если кодов нет — это отказ с
  названной причиной, а не «ещё подождём».

**Тест** (`bot/tests/test_robux_delivery.py`):

* `test_an_order_accepted_for_processing_is_followed_up_not_written_off` —
  покупка отдаёт `IN_PROGRESS`, опрос на втором запросе отдаёт код; код
  доходит до покупателя, покупка вызвана **один раз**.
* `test_polling_stops_on_a_terminal_status_without_codes` — `CANCELLED` без
  кодов → продавцу сказано, покупка не повторяется.

## Правка 5. Коды из `GET /orders` приходят замазанными

**Где:** `bot/automation/approute.py` (`order_by_reference_sync`),
`bot/automation/robux.py` (`codes_from_result`).

**Что сейчас.** `order_by_reference_sync` шлёт `GET /orders?referenceId=…`
без `unhide`, а `codes_from_result` ищет коды в `data.result.vouchers` и
`data.orders[]`.

**Почему это дорого — две независимые поломки:**

1. **Ответ другой формы.** У `GET /orders` коды лежат в
   `data.page.items[].vouchers[].pin`. Такого пути `codes_from_result` не
   знает — значит после обрыва связи мы не найдём код, даже когда он есть.
2. **Коды замазаны.** Без `unhide=true` приходит `****9012`. Почини первое,
   не почини второе — и покупатель получит от бота четыре звёздочки и четыре
   цифры вместо кода. Это ровно та поломка, которой посвящён `CLAUDE.md`:
   бодрый отчёт об успехе там, где выдачи не было.

**Как чинить.**

```python
def order_codes_sync(creds: dict, reference: str) -> dict:
    ref = str(reference or "")[:40]
    ok, data = _guarded(lambda: _client(creds).call(
        "GET", "/orders", params={"referenceId": ref, "unhide": "true"}) or {})
    ...
```

* `unhide=true` **обязателен вместе с фильтром** — без фильтра HTTP 422.
* Читать `data["page"]["items"]`; `codes_from_result` научить этому пути.
* **Отдельная защита от маски** — код, начинающийся с `*`, не код:

```python
def is_masked_code(code: str) -> bool:
    """`****9012` — это замазанный код, а не код.

    Отправить его покупателю значит отчитаться о выдаче, которой не было.
    """
    return str(code or "").lstrip().startswith("*")
```

Такие коды выбрасываются при чтении, и если после этого не осталось ни
одного — это «кода нет», а не «выдали». Проверка нужна не потому, что мы
забудем `unhide`, а потому что забыть его — единственный способ ошибиться
незаметно: ответ приходит успешный, поле на месте, всё выглядит рабочим.

**Побочное действие `unhide=true`**, которое надо знать: поставщик помечает
коды полученными и запоминает время первой выдачи. Значит звать его из
диагностики «просто посмотреть» нельзя — только на пути настоящей выдачи.

**Тест** (`bot/tests/test_robux.py` и `test_robux_delivery.py`):

* `test_a_masked_code_is_never_sent_to_the_buyer` — ответ с `****9012`;
  покупателю не ушло ничего, продавцу сказано.
* `test_codes_are_read_from_the_orders_listing_shape` — форма
  `{"page":{"items":[{"vouchers":[{"pin":"AAAA-BBBB"}]}]}}` разбирается.
* `test_the_lookup_asks_for_unhidden_codes` — в параметрах запроса есть
  `unhide`.

## 6. Как выглядит выдача целиком после пяти правок

```
заказ оплачен (is_paid), название содержит Robux
  ↓
подбор номинала по каталогу (кеш 2 мин; GET /services — 2 запроса в минуту!)
  точное совпадение или отказ; регион учитывается
  ↓
намерение в журнал: {order, robux, denomination, service_id, reference,
                     region, price, chat, state:"собираемся покупать"}   → save
  ↓
GET /services/{service_id}/items/{denomination}      ← замена сухому прогону
  нет в наличии → отказ, денег не потрачено
  ↓
state:"покупаем" → save
POST /orders {"ordersType":"shop","referenceId":…,
              "orders":[{"denominationId":…,"quantity":1}]}
  ↓
statusCode 0/2 + result.vouchers[].pin   → код есть
statusCode 1 (IN_PROGRESS)               → опрос GET /orders?referenceId&unhide
statusCode 9 / 10                        → нет в наличии / нет денег: честный отказ
прочее                                   → отказ с traceId
  ↓
код в запись (state:"куплен, отправляем") → save     ← ДО отправки
  ↓
отправка в чат заказа
  ↓
state:"выдан", order_id в delivered      → save      ← только после отправки
```

Три записи в этом порядке — намерение, код, отметка — переставлять нельзя:
каждая закрывает свой способ потерять деньги. Это уже так и работает, правки
ничего в этом порядке не меняют.

## 7. Что сказать продавцу до первой покупки

Это не «приятно бы», а условие работы; два пункта из трёх не видны никак,
пока не станет поздно.

1. **У ключа должно быть право `orders:write`.** Дословно из кабинета: без
   него ключ покупает, но **кода не отдаёт**. Деньги списаны, выдать нечего.
   Проверяется до покупки одним дешёвым запросом:
   `GET /orders?referenceId=<любая-строка>&unhide=true` — нет прав придёт
   `statusCode: 5` (FORBIDDEN). Это стоит сделать частью экрана доступа.
2. **Права на покупку** — `shop:write` (и/или `product:write`).
3. **У ключа есть `spendLimit`** — потолок трат, `0` = без ограничения. Если
   покупки начнут отказываться «без причины» — смотреть его.
4. **Постоянный ключ требует белого списка IP**, временный живёт 48 часов.
   Если хостинг двухстековый — вписывать и IPv4, и IPv6, иначе адрес будет
   тот, да не тот. Смотреть `/apr_whoami` **с того же адреса**, то есть через
   наш прокси.

## 8. Что проверяется живьём и как это записать

Пока не сделана хотя бы одна настоящая покупка, автовыдачу нельзя считать
рабочей — сухого прогона, которым это можно было бы подменить, у shop нет.
Порядок первой живой проверки, по одному заказу:

1. `/apr_balance` — ключ принят, счёт виден. (Читает `/accounts`, 20/мин.)
2. `/apr_stock robux` — номинал на нужное число Robux есть, `inStock > 0`.
3. `/apr_item <denominationId>` (новая команда) — цена и остаток тем же
   путём, каким их прочтёт выдача.
4. Настоящий заказ на витрине → выдача → **код дошёл покупателю**.
5. Сразу после: `GET /orders?referenceId=…` из `/apr_debug` — сверить, что
   ссылка у поставщика та самая (проверка правки 2).
6. **Проверка идемпотентности:** повторить покупку с той же ссылкой
   (например, поставив заказ в ручную очередь ещё раз). Ожидание —
   `statusCode: 2`, тот же код, **второго списания нет**. Сверить баланс до
   и после.

В `CHECKLIST.md` записывать номером заказа и датой; зелёные тесты
доказательством здесь не считаются.

## 9. Как разделить работу между сессиями

Правки почти не пересекаются по файлам:

| правка | файлы | пересечения |
|---|---|---|
| 1 (конверт) | `automation/approute.py` | с 2 и 3 — один файл, разные функции |
| 2 (`referenceId`) | `automation/approute.py`, `automation/robux.py` | — |
| 3 (сухой прогон) | `approute.py`, `handlers/approute.py`, `tasks/manager.py` | с 4 — `_robux_finish` |
| 4 (опрос) | `approute.py`, `tasks/manager.py` | с 3 — `_robux_finish` |
| 5 (маска) | `approute.py`, `robux.py` | с 2 — `robux.py` |

Разумное деление на двоих: **1 + 2 + 5** (клиент и разбор ответов) одному,
**3 + 4** (порядок выдачи в `manager.py`) второму. Делать 3 и 4 порознь не
стоит — обе трогают `_robux_finish`.

Начинать с правки 1 в любом случае: пока успех определяется угадыванием,
любые проверки остальных правок читаются неверно.
