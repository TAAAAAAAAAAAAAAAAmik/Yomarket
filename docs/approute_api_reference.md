# AppRoute Public API — справочник по официальной документации

**Снято 19.08 с `https://approute.io/api-access?tab=docs`.** Это первый раз,
когда мы читаем документацию поставщика целиком, а не восстанавливаем её по
исходникам SDK. Большую часть того, что было записано в `approute_api_notes.md`, она
подтверждает; четыре вещи — опровергает, и все четыре денежные.

Файл разделён так: сначала **как перепроверить** (потому что бандл панели
пересобирается и хеши меняются), потом факты. Каждый факт помечен, откуда он:

* 📗 — прочитано в документации поставщика;
* 🔬 — снято живым запросом 19.08 (без ключа, читающими вызовами);
* ⚠️ — не проверено ни тем, ни другим.

---

## 0. Как перепроверить всё это

Страница `/api-access?tab=docs` — SPA. `curl` и WebFetch по ней отдают
каркас на 1.6 КБ без единого слова документации; текст лежит в JS-бандле.
Порядок:

```bash
curl -s "https://approute.io/api-access?tab=docs" | grep -o '/assets/index-[^"]*\.js'
curl -s "https://approute.io/assets/index-XXXX.js" -o apr.js
grep -oE 'import\("\./[^"]+"\)' apr.js       # 25 ленивых кусков
# скачать их и найти тот, где есть строка apiAccess.docs — это и есть документация
grep -l 'apiAccess.docs' *.js
```

В нужном куске лежат: словарь текстов на четырёх языках (`et` — английский),
перечень эндпоинтов с примерами запроса и ответа, и enum кодов ответа.
**Хеши в именах файлов меняются при каждом их выкате** — искать по строке
`apiAccess.docs`, а не по имени.

Единственная часть, которую можно перечитать одной командой и без ключа:

```bash
curl -s https://approute.io/api/v1/rate-limits
```

🔬 Он открытый, отвечает `statusCode: 0` и отдаёт лимиты по всем
эндпоинтам. Это же самый дешёвый способ убедиться, что наш разбор конверта
считает успех успехом.

🔬 **Оба домена — один шлюз.** `rate-limits` с `approute.io` и `approute.ru`
совпали побайтно, и `/whoami` без ключа отвечает на обоих одинаково. Прежняя
осторожная формулировка («общий адрес не исключён») теперь лишняя, но кабинеты
и ключи это по-прежнему не объединяет — проверено только то, что API один.

## 1. Конверт один, и он документирован

📗 Прежняя запись «конверта два, и настоящий — не тот, что в SDK» **снята**.
Настоящий конверт ровно один, он описан в документации, и это тот самый,
который мы сняли пробой 17.08:

```json
{"status": "SUCCESS", "statusCode": 0, "statusMessage": "OK",
 "traceId": "trace-id", "data": { }, "errors": null}
```

* `status` — строковый enum, четыре значения (см. §3);
* `statusCode` — **числовой** код приложения; документация прямым текстом
  говорит: *«does not match HTTP status»*;
* `statusMessage` — причина словами;
* `traceId` — по нему поставщик находит запрос у себя;
* `data` — полезная нагрузка, у отказов `null`;
* `errors` — список `{field, code, message}` для отказов по схеме.

🔬 Живой ответ добавляет к этому седьмое поле — `errorCode` (у всех снятых
ответов `null`). В документации его нет; читать его можно, полагаться на
него нельзя.

Конверт `{code, message}` из SDK — **устаревший**. Не «второй конверт», а
просто неверное описание. Ветку разбора по полю `code` можно оставить как
подстраховку, но решать должен `statusCode`.

## 2. `statusCode` — числовой enum, и это ответ на вопрос «получилось ли»

📗 Взято из самого бандла документации (`V={OK:0,…}`):

| код | имя | значение |
|---:|---|---|
| 0 | `OK` | получилось |
| 1 | `ACCEPTED` | **принято в работу**, результата ещё нет |
| 2 | `IDEMPOTENCY_REPLAY` | тот же `referenceId` — отдаётся первый результат |
| 3 | `VALIDATION_ERROR` | отказ по схеме, подробности в `errors[]` |
| 4 | `UNAUTHORIZED` | ключ не принят |
| 5 | `FORBIDDEN` | не хватает прав или IP не в белом списке |
| 6 | `NOT_FOUND` | товар или заказ не найден |
| 8 | `LIMIT_REACHED` | упёрлись в лимит запросов |
| 9 | `OUT_OF_STOCK` | нет в наличии |
| 10 | `INSUFFICIENT_FUNDS` | не хватает средств |
| 11 | `UPSTREAM_ERROR` | сбой у вышестоящего поставщика |

Семёрки в enum нет вовсе. Неизвестный код — отказ.

**Успех — это 0, 1 и 2.** Ровно те же три, что были в SDK по именам, но
числами. 🔬 Проверено на живом ответе: `/whoami` без ключа → `statusCode: 4`,
`statusMessage: "API key required"`, `status: "CANCELLED"`; `rate-limits` →
`statusCode: 0`, `status: "SUCCESS"`.

> **Это опровергает наш нынешний разбор.** `_live_envelope_is_ok` в
> `bot/automation/approute.py` считает успехом только `statusCode` из
> `("200","201","0","")`. Значит `1` (ACCEPTED) и `2` (IDEMPOTENCY_REPLAY)
> читаются как **отказ**. Первое — «заказ создан, но мы доложили о провале»,
> второе — «повтор после обрыва принят за отказ», то есть вторая покупка.
> Обе поломки — ровно те, ради которых в `CLAUDE.md` написано правило 1.

## 3. `status` — строковый enum из четырёх значений

📗 `SUCCESS | IN_PROGRESS | PARTIALLY_COMPLETED | CANCELLED`

* `IN_PROGRESS` — приходит с **HTTP 202** и `statusCode: 1`. Заказ принят,
  кода в ответе нет (`result: null`). Дальше — опрос.
* `PARTIALLY_COMPLETED` — **терминальный**: выполнено частично, часть кодов
  может отсутствовать. Не «ещё подождать».
* `CANCELLED` — терминальный отказ.

📗 Совет самой документации по опросу: начинать с 1–2 секунд, дальше
экспоненциально, останавливаться на терминальном статусе.

## 4. Заголовки

📗 `X-API-Key: <ключ>` — и всё. Для запросов с телом (POST/PUT/PATCH)
обязателен `Content-Type: application/json`, **иначе HTTP 415**. Наш клиент
шлёт его всегда — это верно.

## 5. `POST /orders` — тело

📗 Наша форма, выясненная сухим прогоном 18.08, **подтверждена** — с одной
денежной поправкой в имени поля.

```json
{"ordersType": "shop",
 "referenceId": "my-reference-001",
 "orders": [{"denominationId": "8a5a2d77-…", "quantity": 1, "isLongOrder": false}]}
```

| поле | правило |
|---|---|
| `ordersType` | `"shop"` (коды) · `"dtu"` (прямое пополнение) · `"esim"` |
| `referenceId` | **обязателен для покупок**, 1..40 символов, уникален в пределах нашего кабинета. Это и есть ключ идемпотентности |
| `orders` | **ровно одна позиция** (`minItems=1, maxItems=1`) |
| `orders[0].denominationId` | `id` номинала из каталога |
| `orders[0].quantity` | сколько штук |
| `orders[0].isLongOrder` | «долгий заказ», только для shop (см. §9) |
| `orders[0].fields` | `[{key, value}]` — нужны некоторым товарам, у DTU обычно `account_reference` |
| `orders[0].amountCurrencyCode` | только DTU, для открытых диапазонов |
| `checkOnly` | **только `ordersType=dtu`** |

### 5.1. Поле называется `referenceId`, а не `reference`

📗 В документации `reference` как поле запроса **не существует вовсе**. Оно
есть только в *ответе* `GET /orders` (эхо нашего значения в строке заказа).

> **Это опровергает нашу правку от 18.08** («из двух имён берётся
> `reference`»). `live_order_body` кладёт наверх `reference`, и раз такого
> поля в схеме нет, идемпотентности у нас сейчас **нет**: повтор после
> обрыва — вторая покупка за свои деньги. Это самая дорогая из четырёх
> найденных сегодня ошибок.

📗 Как работает идемпотентность: повтор с тем же `referenceId` возвращает
**первый сохранённый результат** и `statusCode: 2`. Тело запроса при этом
игнорируется — расхождение тела не даёт 409. Совет документации: генерировать
UUID на заказ (нам не годится — наша ссылка обязана быть выводима из номера
заказа, чтобы пережить перезапуск; см. план).

### 5.2. Сухого прогона для магазина нет

📗 `checkOnly`: *«Allowed only for `ordersType=dtu`»*. Отдельным методом в
документации он и назван — «DTU Check», и делает он проверку + котировку у
вышестоящего поставщика, не создавая заказа.

Robux у AppRoute — `voucher`, то есть `ordersType=shop`. Значит **сухого
прогона перед покупкой Robux не существует**, и весь наш замысел «проверим
форму, потом купим» держаться ему не на чем.

> Это закрывает пункт, который висел как блокирующий («сухой прогон с
> настоящим `denominationId` не сделан — выдачу писать нельзя»). Он не будет
> сделан никогда. Чем его заменить — §2 плана.

## 6. Ответы `POST /orders`

📗 Примеры из документации, для `ordersType=shop`:

```jsonc
// HTTP 202 — принято в работу
{"status":"IN_PROGRESS","statusCode":1,"statusMessage":"OK","traceId":"…",
 "data":{"orderId":"order_123","status":"IN_PROGRESS","price":10.5,
         "currency":"USD","result":null},"errors":null}

// HTTP 200 — готово
{"status":"SUCCESS","statusCode":0,"statusMessage":"OK","traceId":"…",
 "data":{"orderId":"order_123","status":"SUCCESS","price":10.5,"currency":"USD",
         "result":{"vouchers":[{"pin":"1234-5678-9012","serialNumber":"SN-0001",
                                "expiration":null}],"attributes":null}},"errors":null}

// HTTP 200 — повтор по той же ссылке
{"status":"SUCCESS","statusCode":2,"statusMessage":"Idempotent replay", …}

// HTTP 422 — нет в наличии / не хватает денег
{"status":"CANCELLED","statusCode":9,"statusMessage":"insufficient stock","data":null}
{"status":"CANCELLED","statusCode":10,"statusMessage":"insufficient user balance","data":null}
```

`pin` — это и есть код гифт-карты. Путь к нему: `data.result.vouchers[].pin`.
📗 У DTU `vouchers` всегда `null`, результат в `result.attributes`; у eSIM —
в `result.esim`.

## 7. `GET /orders` — коды приходят **замазанными**

📗 Это то, чего мы не знали вовсе, и оно ломает восстановление после обрыва.

* Без `orderId` и без `referenceId` коды замазаны **всегда**, и запрос без
  побочных действий.
* С фильтром — по умолчанию тоже замазаны.
* Полные коды отдаются только по `?referenceId=…&unhide=true` (или
  `?orderId=…&unhide=true`).
* 📗 Формат маски строгий: `****` + последние 4 символа → `****9012`.
* 📗 `unhide=true` **без фильтра** — HTTP 422.
* 📗 У `unhide=true` есть намеренное побочное действие: коды помечаются
  полученными, и запоминается время первой выдачи.

Форма ответа — **не такая, как у `POST /orders`**:

```json
{"data":{"page":{"items":[{"orderId":"order_123","reference":"my-reference-001",
   "serverTime":"…","status":"SUCCESS","itemId":"8a5a…","quantity":1,
   "amount":10.5,"currency":"USD","accountNumber":null,
   "vouchers":[{"pin":"****9012","serialNumber":"SN-0001","expiration":null}]}],
   "hasNext":false}}}
```

> **Два наших дефекта разом.** `order_by_reference_sync` не шлёт `unhide`,
> а `codes_from_result` ищет коды в `data.result.vouchers` и `data.orders[]`
> — пути `data.page.items[].vouchers` он не знает. То есть после обрыва мы
> либо не найдём код вовсе, либо (после починки пути) отправим покупателю
> `****9012`.

## 8. Каталог

📗 `GET /services` → `data.items[]`. У услуги: `id`, `name`, `type`
(`voucher` | `direct_topup` | `esim`), `countryCode`, `section`,
`categoryName`, `subcategoryName`, `fields` (схема полей заказа или `null`),
и вложенный `items[]` — номиналы:

```json
{"id":"denom_10","name":"10 USD","nominal":10,"price":10.5,"currency":"USD",
 "inStock":42,"isLongOrder":true,"minQtyToLongOrder":2}
```

📗 **Постраничное чтение появилось** (прежняя запись «дочитать список нечем»
устарела): `type`, `search` (1..200 символов, без учёта регистра), `limit`
(1..500), `offset`. При заданном `limit` в ответе приходит `total`, и читать
надо `offset += limit`, пока `offset >= total`. Без `limit` — прежний полный
список целиком.

Ещё два способа читать каталог, которых мы не использовали:

* 📗 `GET /services/{serviceId}/items/{itemId}` — один номинал, ответ
  побайтно совпадает с соответствующим элементом `items[]`. Прямо назван
  как способ **освежить цену и остаток одного номинала**, не перечитывая
  весь каталог. Лимит 120/мин.
* 📗 `POST /services/items/lookup` — до 100 пар `(serviceId, itemId)` за
  запрос, всегда HTTP 200, отсутствие услуги или номинала роняет только свою
  строку (`error=service_not_found` / `item_not_found`). Лимит 30/мин.

## 9. Долгие заказы (`isLongOrder`)

📗 Для некоторых номиналов поставщик не держит запас; коды генерируются по
требованию и **приходят позже**. В каталоге у номинала есть `isLongOrder`
(поддерживается ли) и `minQtyToLongOrder` (с какого количества можно).
Включается флагом `orders[0].isLongOrder=true`, только для shop.

Такой заказ дольше висит в `IN_PROGRESS`. Мы этот флаг **не ставим и ставить
не должны** — но обязаны понимать, что `IN_PROGRESS` бывает и без него.

## 10. Лимиты запросов

🔬 Снято живьём (`GET /api/v1/rate-limits`, 19.08). Умолчание — 1000/60 с,
область действия — «на кабинет и на эндпоинт».

| метод | путь | лимит/мин |
|---|---|---:|
| GET | `/accounts` | 20 |
| GET | `/accounts/transactions` | 10 |
| GET | `/funds/invoices` | 10 |
| GET | `/funds/methods` | 20 |
| **GET** | **`/orders`** | **2** |
| **GET** | **`/services`** | **2** |
| GET | `/services/{id}` | 60 |
| GET | `/services/{service_id}/items/{item_id}` | 120 |
| GET | `/steam-currency/rates` | 1000 |
| GET | `/whoami` | 1000 |
| POST | `/funds/invoices` | 5 |
| **POST** | **`/orders`** | **120** |
| POST | `/services/items/lookup` | 30 |

📗 Документация уточняет то, чего в этой таблице не видно: у `GET /orders`
лимит зависит от запроса — **без фильтров 2/мин, с `orderId`/`referenceId`
20/мин, а с `unhide=true` — 5/мин по отдельному счётчику**. Превышение →
HTTP 429 со `statusCode: 8`.

Что из этого следует для нас:

* **`GET /services` — 2 запроса в минуту.** Наш кеш каталога на 120 секунд
  впритык укладывается ровно в один запрос на продавца; при двух продавцах
  на одном ключе — уже нет. Каталог целиком читать редко, а перед покупкой
  освежать **один номинал** (120/мин).
* **Опрос `IN_PROGRESS` — не чаще раза в 12 секунд** (5/мин), и это на весь
  кабинет, а не на заказ.

## 11. Права ключа (scopes)

📗 Ключ выдаётся с правами по разделам, отдельно чтение и запись. Названия и
что каждое даёт — из кабинета:

| раздел | read | write |
|---|---|---|
| `shop` | список товаров и номиналов магазина | **покупки в магазине** |
| `product` | список номиналов | **покупка товаров** |
| `orders` | список заказов | **получение кодов**; включение обновляет отметку времени выдачи |
| `direct_topup` | номиналы DTU | пополнения DTU |
| `funds` | счета и способы пополнения | создание заявок на пополнение |
| `transaction` | история операций | — |
| `dashboard` | статистика | — |

**Самое опасное здесь — `orders:write`.** Дословно: *«Allows retrieving
digital codes for orders. If disabled, codes cannot be obtained with this API
key.»* То есть ключ без него **покупает, но кода не отдаёт**. Деньги
списаны, покупателю выдать нечего. Об этом продавцу надо сказать до первой
покупки, а не после.

📗 Для eSIM отдельного права нет — используются `product:read` +
`orders:write`/`orders:read`.

## 12. Ключи: временный и постоянный

📗 Подтверждает то, что продавец говорил со слов кабинета:

* **Временный** — до 48 часов, белый список IP не обязателен.
* **Постоянный** — белый список IP **обязателен**.
* Записи белого списка: IPv4 (`13.48.112.9`), IPv4 с маской (`192.168.*.*`),
  CIDR (`10.0.0.0/8`), IPv6 и IPv6 CIDR. Несколько — через запятую или
  пробел. **Если хостинг двухстековый, вписывать и IPv4, и IPv6.**
* У ключа есть ещё `spendLimit` — потолок трат, `0` = без ограничения.
  Про него мы не знали; если у продавца покупка отказывается «без причины»,
  это одна из версий.
* Кабинет прямым текстом советует проверить адрес командой на `/whoami`
  **с того сервера, где работает интеграция** — то есть `/apr_whoami` через
  прокси делает ровно то, что предписано.

## 14. Что этим НЕ выяснено

⚠️ Ни один вызов с настоящим ключом сегодня не делался — ключа в этой
сессии нет. Всё, что помечено 📗, прочитано в документации поставщика, а не
увидено в ответе на нашу покупку. Живой проверки по-прежнему требуют:

1. **Что придёт на настоящую покупку Robux** — 200 с кодом или 202 с
   `IN_PROGRESS`. От этого зависит, обязателен ли опрос (мы пишем его в
   любом случае).
2. **Есть ли у ключа продавца `orders:write`.** Проверяется до покупки:
   `GET /orders?referenceId=что-угодно&unhide=true` — если прав нет, придёт
   `statusCode: 5` (FORBIDDEN), и это дешёвая проверка.
3. **Держится ли идемпотентность на `referenceId`** — проверяется только
   настоящей повторной покупкой, то есть на первом же живом заказе.
4. ⚠️ **`spendLimit` у ключа продавца** — неизвестен.
