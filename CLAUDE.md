# Работа над ботом Юмаркет

Бот автоматизации продаж для продавцов маркетплейса Юмаркет (цифровые товары:
игровая валюта, аккаунты, ключи, Telegram Stars). Telegram-бот на aiogram 3.30.

**Это продукт, который продаётся по подписке другим продавцам, а не личный
скрипт.** Отсюда всё остальное в этом файле: чужие деньги, чужие покупатели,
чужие seed-фразы. Решение «и так сойдёт, я же знаю, как оно работает» здесь
неприменимо — тот, кто заплатил за подписку, не знает.

Язык всего: ответы пользователю, тексты в интерфейсе, сообщения коммитов,
докстринги и комментарии — **русский**. Имена в коде английские.

---

## Главное правило: бот не должен врать

Самая частая и самая дорогая поломка в этом проекте — не падение, а **бодрый
отчёт об успехе там, где ничего не произошло**. Реальные примеры:

- «✅ Пак поднят · Поднято: 0»
- «Цена изменена» — при том, что в панели у товара вообще нет поля цены
- «Автоответ не дошёл… ответьте вручную» — в чат, куда маркетплейс не пустит
  и человека
- «🔍 Почему молчит» отвечал «не молчал», потому что причина не записывалась

Отсюда рабочие требования:

1. **HTTP 200 — не доказательство.** Сделали изменение — перечитайте и
   сравните. `panel_update_item_sync` так и устроен.
2. **Каждое «ничего не произошло» объясняется.** Пропустили сообщение,
   не ответили, не подняли — запишите причину туда, где её увидит продавец
   (`conf["last_skip"]`, журнал автоответов, `poll["error"]`).
3. **Догадка не подаётся как факт.** Если отказ ещё не случился — так и
   пишите: «скорее всего не пройдёт, здесь это ещё не проверялось». Образец —
   шаг 5 в `_chain_report` (`bot/handlers/chats.py`).
4. **Не советуйте невозможного.** `explain_error` (`bot/autoreply.py`)
   возвращает вторым значением «можно ли исправить вручную» — совет зависит
   от него.
5. **Английский код ошибки на экране продавца — это отписка.** Переводите.

## Метод: сначала диагностика, потом починка

Каждая многочасовая яма в этом проекте начиналась с догадки о том, что
возвращает сервер. Каждая закрывалась read-only командой, печатающей факты.

Прежде чем чинить непонятное — **напишите диагностику, которая покажет, что
происходит на самом деле**, и дайте её пользователю. Существующие (полный
список — в `CHECKLIST.md`):

| Команда | Что показывает |
|---|---|
| `/version` | версия, хранилище, токен, куки панели |
| `/chat_debug <заказ>` | всю цепочку по чату: очередь опроса → сообщения → отметка «дочитано» → правило и пауза → примет ли маркетплейс ответ |
| `/order_debug <заказ>` | по одному заказу: цена в списке против цены в карточке, сырой статус, почему не взят в работу |
| `/stats_debug` | откуда взяты цифры статистики |
| `/panel_map`, `/panel_debug` | разделы панели |
| `/fragment_debug`, `/stars_probe <ник>` | сессия Fragment и покупка звёзд |
| `/fragment_cookies` | переписывает ли страница покупки наши куки — проба под версию про «Access denied» |
| `/ns_stock <слово>` | каталог поставщика ns.gifts: service_id, цена, остаток и схема полей заказа |
| `/apr_stock <слово>`, `/apr_balance` | каталог и баланс AppRoute — выбранного поставщика: serviceId, itemId, цена за номинал, поля заказа |
| `/apr_whoami` | каким IP нас видит AppRoute — у него белый список адресов, а на Railway адрес меняется при каждом выкате |
| `/apr_debug` | сырой ответ AppRoute по обоим кабинетам: статус, поля тела, `code`, `traceId` — написана после отказа «HTTP 200» без конверта |
| `/health` (по `PORT`) | версия, хранилище **и приём обновлений**: `status: deaf` означает «процесс жив, но Telegram нас не слышит» |

Отдельно: **не управляйте логикой по тексту собственного отчёта.** Был случай
`guest = any("не видно входа" in line for line in report)` — разбор своей же
прозы вместо структурных данных. Факты собирайте в dict.

## Что уже известно про API — не выясняйте заново

Это стоило часов. Проверено на живом магазине.

### Integration API — `https://api.yoo.market/integration/v1`, Bearer-токен

- **Цена приходит объектом**, не числом:
  `{"amount": 129, "base_amount": 129, "currency": "RUB"}`.
  Читать только через `orderfields.ad_price` / `order_price`.
- **Сообщения лежат под чатом, а не под заказом:** `GET /chats/{chat_id}/messages`.
  Номер чата ≠ номер заказа; он сохранён в `known_order_details[oid]["chat_id"]`.
- **Переписка отдаётся от новых к старым.** Порядок нормализован в `_msg_rows`
  (`bot/tasks/manager.py`) — все читатели идут через него. Не сортируйте
  заново и не берите `rows[-1]` до нормализации.
- **Номера сообщений сквозные** для всего маркетплейса, не для чата.
- **В закрытый заказ писать нельзя:** `no_active_orders_in_chat`. Ни боту, ни
  продавцу вручную.
- **Чего в API нет вовсе:** поднятия объявлений, вывода средств, отзывов,
  изменения цены. Всё это — через панель. Методы `bump_ad`, `bump_all_ads`,
  `withdraw_balance`, `get_reviews` были удалены; тест
  `test_dead_buttons.py` следит, чтобы они не вернулись.

### Панель Nova — `https://panel.yoomarket.net`, сессионные куки

- Вход по email + одноразовый код (`/token`, `/code`).
- Обновление: `POST /nova-api/{resource}/{id}/update-fields` с `_method=PUT`.
- **У товара (`items`) нет поля цены.** Менять цену из бота невозможно в
  принципе — функция снята намеренно, осталась только видимость стоимости.

### Fragment (звёзды)

**Истина здесь — документация рабочего клиента, которую дал продавец.** Где
наша реализация с ней расходилась, расхождение убрано; своих вариантов тут
не сочиняем. Расхождения стоили нам дня на A1.

- **Всё уходит в строку запроса:** `method`, `hash` и аргументы. У нас было
  по-своему (метод и аргументы в теле) — поиск получателя проходил, а
  покупка отвечала «Access denied».
- **Заголовок один — `User-Agent`.** Свои `X-Requested-With`, `Origin`,
  `Referer` добавлялись по догадке и убраны.
- **`searchStarsRecipient` шлёт только `query`.** Наш `quantity` был
  домыслом по форме на сайте.
- **Хеш всегда читается со страницы покупки** `/stars/buy` — и из HTML, и
  из подключённых JS, по именам `hash`, `csrf`, `token`, `nonce`,
  `signature`, `sig`. Зашитого значения больше нет: чужой хеш был первой
  из пяти причин, по которым выдача не работала.
- **Аккаунт и привязанный кошелёк проверяются на `/my/profile`.**
- Цепочка: `searchStarsRecipient` → `initBuyStarsRequest` →
  `getBuyStarsLink` → подпись BOC → TonCenter `sendBoc` → ждать `seqno` →
  `confirmReq`. `recipient` берётся из `found.recipient`, а не из ника.
- Куки различаются по форме: `stel_ssid` = `hex_цифры`, `stel_token` = чистый
  hex, `stel_ton_token` — длинный base64url. `guess_cookie_name` расставляет
  их сама, потому что пользователи их путают.
- Признак входа — **только** `/logout` или `my assets` на странице. `ton-auth`
  — это кнопка «Connect TON», то есть признак ОБРАТНОГО.
- Адреса TON: `EQ…`, `UQ…` и `0:hex` — одно и то же. Сравнивать через
  `wallet_hash`, а не строкой.

### AppRoute — `https://approute.io/api/v1`, заголовок `X-API-Key`

**Выбранный поставщик** для автовыдачи Robux (решение продавца, 17.08).
Истина по этому API — исходники официального SDK и `openapi.yaml`, разобранные
в `docs/approute_api_notes.md`. Клиент — `bot/automation/approute.py`, только
чтение: покупки не написано, пока не увиден живой каталог.

- **HTTP 200 — не ответ на вопрос «получилось ли».** Снаружи ответ всегда
  двухсотый; всё существенное лежит в конверте.
- **Конверта два, и настоящий — не тот, что в SDK.** SDK описывает
  `{status, code, message, traceId, data}`, успех — `code` из трёх (`OK`,
  `ACCEPTED`, `IDEMPOTENCY_REPLAY`). А живой ответ (проба на настоящем ключе
  17.08, оба домена одинаково) —
  `{data, errorCode, errors, status, statusCode, statusMessage, traceId}`:
  ни `code`, ни `message` нет вовсе, код отказа в `errorCode`, причина
  словами в `statusMessage`, значимый числовой код в `statusCode` **внутри
  тела**. Бот понимает оба. Признак успеха во втором выведен из имён полей,
  а не из документации, поэтому спорный ответ считается отказом: принять
  отказ за успех значит отчитаться о выдаче, которой не было.
- **`IDEMPOTENCY_REPLAY` — это успех, а не отказ:** «такой заказ уже был,
  отдаю прежний результат». Принять его за отказ значит потерять оплаченный
  заказ и купить второй раз.
- **На проводе camelCase.** В SDK поля пишутся `item_id`, `reference_id`,
  `client_time`, но его транспорт переводит их в `itemId`, `referenceId`,
  `clientTime` **перед отправкой**, а ответ переводит обратно. Мы идём без
  SDK — значит camelCase пишем и читаем сами.
- **`traceId` печатается в каждом отказе:** по нему поставщик находит запрос
  у себя.
- **Отказы уже разделены самим API** (`OUT_OF_STOCK`, `INSUFFICIENT_FUNDS`,
  `LIMIT_REACHED`, `UPSTREAM_ERROR`, …) — различать не надо, переводить надо.
- **Кабинета два:** `approute.io` и `approute.ru`. Их README говорит брать
  ключ в «своём», но экран выдачи ключа в `approute.ru` предлагает проверять
  его запросом на **approute.io** — общий адрес не исключён, и утверждать
  обратное мы не можем. `/apr_debug` спрашивает оба и печатает, где ключ
  приняли.
- **Ключей два вида** (со слов продавца): временный на 48 часов и
  постоянный; белый список IP нужен постоянному. В SDK и OpenAPI про это
  ничего нет. Поэтому «ключ не принят» называет три причины сразу: срок,
  белый список, не тот кабинет.
- **По виду ключ не проверяется.** В README примеры `sk_live_…`, а кабинет
  выдал `wli-…` — проверка формы отвергала бы настоящий ключ.
- **У них белый список IP.** Об этом нет ни слова ни в SDK, ни в OpenAPI —
  сказано только на экране выдачи ключа, вместе с проверочной командой на
  `GET /whoami` (этого вызова тоже нет в SDK). Бот живёт на Railway, где
  адрес меняется при каждом выкате, поэтому «ключ не сработал» после деплоя
  означает обычно именно это. Смотреть `/apr_whoami`.
- **Лечится прокси с постоянным адресом** — в белый список вписывается он,
  а не сервер. Задаётся кнопкой «🌐 Прокси» на экране доступа, шифруется в
  хранилище (в строке логин и пароль), показывается только хостом и портом.
  **Через него обязаны идти и рабочие вызовы, и диагностика:** проба, ходящая
  мимо прокси, показывает адрес, с которого поставщик нас не видит. Одна
  точка на весь модуль — `_session`. Годится ли прокси, проверяется, а не
  советуется: «🧪 Годится ли он» спрашивает адрес трижды и сверяет с прямым —
  ловит и ротацию, и не применившийся прокси.
- **`/apr_debug` печатает значения, а не имена полей.** Первая версия
  напечатала «поля тела: data, errorCode, …» — и на этом остановилась, а
  ответ на вопрос «что не так» лежал в значении `statusMessage`. Перечень
  имён без значений отвечает «форма не та» и молчит о причине.
- **Баланс только в USDT** — у ns.gifts он в USD. Сравнивая закупку, сравнивать
  надо не числа, а деньги.
- **Каталога нет ни в SDK, ни в OpenAPI.** Есть ли Roblox, под каким `itemId`
  и почём — знает только живой ответ `GET /services` (`/apr_stock`).
  Постраничного чтения каталога не описано: если пришёл `hasNext`, дочитать
  нечем, и бот говорит об этом прямо.
- **Ещё не выяснено (важно до первой покупки):** тело `POST /orders` в SDK и в
  `openapi.yaml` описано **по-разному** — SDK шлёт `orders_type`/`reference_id`,
  а схема требует `clientTime` + `reference` и запрещает лишние поля. Пока не
  сверено живым вызовом, выдачу писать нельзя.

### Ограничения Telegram

Сообщение — 4096 символов, `callback_data` — 64 байта. Любой текст с
маркетплейса (название магазина, товара, письмо покупателя) перед вставкой в
HTML-сообщение экранируйте: одиночный `<` роняет всю отправку.

## Безопасность

**Куки Fragment и seed-фраза TON никогда не попадают в логи, в отчёты
диагностики и в репозиторий.** В диагностике печатается только длина
(«stel_token: 39 символов»), не значение. Это доступ к чужому кошельку.

**Seed-фраза шифруется в хранилище** ключом из `SECRET_KEY` (или
`FRAGMENT_KEY`). Подстраховки «ключа нет — выведем свой» нет намеренно: ключ,
собранный из того, что лежит рядом с шифротекстом, шифрованием не является.
Нет ключа — храним как раньше, и `/version` говорит об этом прямо, а не
делает вид. Ключ приводится к нужной длине хешем, а не обрезанием.

На Railway `SECRET_KEY` **обязателен**: без него фраза лежит открытой в той
же базе, куда ходит не только бот.

## Тесты

Живут в `bot/tests/`, запускаются так:

```bash
cd bot && python -m unittest discover -s tests -p "test_*.py"
```

Правила, каждое из которых написано кровью:

1. **Имя теста — предложение о поведении**, не о функции:
   `test_a_closed_chat_does_not_advise_answering_by_hand`. Докстринг класса
   объясняет, какая беда случалась раньше.
2. **Прогоняйте в перемешанном порядке.** `test_dead_buttons` подменял
   `promo_params` без отката, и тринадцать чужих тестов падали «сами по себе».
   Подменяете что-то в общем модуле — откатывайте в `tearDown`.
3. **Тесты пишутся до `if __name__ == "__main__"`.** Дописанные после — просто
   не выполняются.
4. **Проверяйте следствие, а не текст.** В платных функциях проверяется, какой
   товар списан и сколько раз, а не как выглядит сообщение.
5. Ловите утверждение, которое нельзя проверить: если тест не падает при
   откате правки — он ничего не проверяет. Убедитесь, что падает.

## Совместная работа сессий

Рабочая ветка: **`claude/where-we-left-off-mul8tu`**. В другие не пушить.

1. **`CHECKLIST.md` — общий журнал приёмки.** 27 проверок, статусы, что уже
   найдено. Отмечать пункты только по живой проверке на настоящем магазине;
   зелёные тесты доказательством не считаются. Рядом с отметкой писать, чем
   подтверждено (номер заказа, дата).
2. **Перед коммитом — `git pull --rebase`.** Соседний пункт мог отметить
   другая сессия.
3. **`BOT_VERSION` в `bot/handlers/start.py` поднимается при каждом значимом
   изменении.** По нему `/version` показывает, доехал ли код. Без этого
   невозможно отличить «не работает» от «не задеплоено».
4. **Имена команд уникальны.** Две команды с одним именем — не ошибка, а
   тишина: побеждает роутер, подключённый раньше в `main.py`. Так молча не
   работали `/chat_debug` и `/withdraw_debug`. Тест в `test_chat_chain.py`
   разбирает `handlers/*.py` в AST и падает на дубле.
   Вторая причина той же тишины — **брошенная форма**: экран, ждущий ввода,
   ловит любое сообщение, включая команду, и таких экранов девяносто три.
   Внешний middleware `CommandsEscapeForms` (`main.py`) закрывает
   незаконченную форму, когда пришла команда, и говорит об этом вслух.
5. Пул-реквесты не создавать, пока не попросят.
6. **`docs/HANDOFF.md` — состояние на последнюю передачу**: что закрыто, что висит, и какие версии уже опровергнуты. Читать до первого коммита, обновлять при передаче.

## Деплой

Два пути, подробно — `docs/DEPLOY.md`.

1. **Railway** собирает и выкатывает при пуше в подключённую ветку
   (`railway.json` + `Dockerfile`, Chromium в образе нет). Вручную —
   `railway up`.
2. **Свой сервер по SSH** — `.github/workflows/deploy-bot.yml` запускает
   `scripts/deploy.sh` при пуше в рабочую ветку и по кнопке «Run workflow»
   на github.com (это же способ обновиться с телефона). Нужны секреты
   `SSH_HOST`, `SSH_USER`, `SSH_KEY`, `DEPLOY_PATH`; пока их нет, workflow
   падает с красным крестом — и это правда, автовыкат не настроен.

**Проверять `/version` после деплоя** — правило прежнее: если версия старая,
код не доехал, и «функция не работает» означает совсем другое. Скрипт выката
делает эту проверку сам, через `/health` (он отдаёт `BOT_VERSION`), и при
несовпадении объявляет выкат неудачным и откатывает код. Health-сервер
поднимается только при заданной переменной `PORT`; без неё сверять нечем, и
скрипт говорит об этом прямо, а не молчит.

**Два бота с одним токеном конфликтуют.** Telegram отдаёт обновления одному
потребителю: если бот останется и на Railway, и на своём сервере, часть
сообщений будет теряться, а в логах будет `Conflict: terminated by other
getUpdates request`. Со стороны продавца это выглядит как «отвечает через
раз» — или как полная тишина, если второй экземпляр забрал приём целиком.

**Вторая причина той же немоты — вебхук на токене.** Пока он стоит, Telegram
**не отдаёт обновления опросом вообще**, а отправка работает: уведомления о
заказах приходят, на команды бот не отвечает. Экземпляр при этом один, и
подсказка про «второй бот» уводит в сторону — так и случилось 17.08.
`clear_webhook` в `main.py` снимает его при запуске (не выбрасывая
накопленные обновления — это заказы) и говорит об этом владельцу: снятие
меняет настройку токена.

**Обе причины приходят как 409 Conflict, и различать их обязательно** —
лечатся они противоположными действиями. Если текст Telegram не называет
причину прямо, `polling_trouble` так и пишет: «причины две», а не выбирает
одну наугад.

**aiogram проглатывает эту ошибку молча:** `_listen_updates` ловит *любое*
исключение, пишет строчку в лог и повторяет вечно. Процесс жив, порт слушает
— а бот глухой. Поэтому в `main.py` есть `WatchPolling`: он слушает логгер
`aiogram.dispatcher`, пишет владельцу (отправка работает, конфликтует только
получение), показывает состояние в `/health` (`status: deaf`) и в `/version`.
Выкат тоже об этом скажет: версия совпала, а бот не слышит — разные вещи.

## Где что лежит

```
bot/
  main.py               порядок подключения роутеров (важен для имён команд)
  storage.py            настройки, токены, куки; PostgreSQL или JSON-файлы
  orderfields.py        разбор ответов API: цена, статус, ник, чат
  autoreply.py          подбор правил, пауза, лимиты, explain_error
  api/yoomarket.py      Integration API
  automation/
    panel.py            панель Nova: вход, товары, продвижение, отзывы
    fragment.py         Fragment + TON: сессия, api-hash, покупка звёзд
    position.py         слежение за позицией на витрине
    market.py           чтение витрины
  tasks/manager.py      фоновый цикл: заказы, чаты, автоответы, автовыдача
  handlers/             экраны бота, по разделам
  tests/                24 файла, 1551 тест
scripts/deploy.sh       обновление бота на сервере со сверкой версии
```

Хранилище: `DATABASE_URL` → PostgreSQL. Без него — JSON-файлы, **которые на
Railway стираются при редеплое**. `/version` это показывает.
