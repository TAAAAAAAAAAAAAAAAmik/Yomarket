# Поставщик кодов AppRoute

Эта половина шаблона **переносится на любую площадку без правок**: поставщик
не знает и знать не должен, откуда пришёл заказ.

Всё ниже проверено живыми вызовами на настоящем ключе. Где документация
поставщика и его же SDK расходились — верх брало то, что приходит на самом
деле.

Адрес: `https://approute.io/api/v1`, авторизация — заголовок `X-API-Key`.

---

## Конверт ответа

**HTTP 200 ничего не значит.** Снаружи ответ почти всегда двухсотый;
получилось ли — решает `statusCode` **внутри тела**. Документация прямо
предупреждает, что они не совпадают.

```json
{"status": "...", "statusCode": 0, "statusMessage": "...",
 "traceId": "...", "data": {...}, "errors": []}
```

### Успехов три, а не один

| Код | Имя | Что значит |
|---|---|---|
| `0` | OK | куплено, код в ответе |
| `1` | ACCEPTED | **заказ принят, код будет позже** — ждать опросом |
| `2` | IDEMPOTENCY_REPLAY | **такой заказ уже был, отдаю прежний результат** |

Разбор, считающий успехом только `0`, читает принятый заказ и законный повтор
как отказ — и покупает второй раз. Это была настоящая поломка.

`IDEMPOTENCY_REPLAY` — это **успех**. Принять его за отказ значит потерять
оплаченный заказ и купить второй раз за свои деньги.

### Отказы

`3` VALIDATION_ERROR · `4` UNAUTHORIZED · `5` FORBIDDEN · `6` NOT_FOUND ·
`8` LIMIT_REACHED · `9` OUT_OF_STOCK · `10` INSUFFICIENT_FUNDS ·
`11` UPSTREAM_ERROR. Семёрки в перечне нет; неизвестный код — отказ.

`traceId` печатается в каждом отказе: по нему поставщик находит запрос у себя.
Выброшенный, он превращает разбор в переписку.

### Отказ по схеме лежит не там, где его ищут

`errorCode` пуст, `code` нет вовсе, а причина — в `errors[]`
(`{field, code, message}`, с повторами). Разбор, смотрящий только на код,
отвечает «непонятно» на ответ, где сервер прямым текстом назвал недостающие
поля.

### Статусы заказа

`SUCCESS` · `IN_PROGRESS` · `PARTIALLY_COMPLETED` · `CANCELLED`.

`IN_PROGRESS` приходит с пустым результатом: заказ создан, кода ещё нет.
`PARTIALLY_COMPLETED` — **терминальный**, а не «ещё подождать».

## Покупка

```json
POST /orders
{"ordersType": "shop",
 "referenceId": "pk-robux-12345",
 "orders": [{"denominationId": "…", "quantity": 1}]}
```

Три вещи, каждая выяснена пробой и каждая денежная:

**1. Позиции списком, `denominationId` внутри.** Ни SDK (`itemId` наверху),
ни `openapi.yaml` (`clientTime` + `reference`) не угадали. `denominationId` —
это `id` **номинала**, а не услуги.

**2. `referenceId` кладётся НАВЕРХ.** Внутри позиции такого поля нет вовсе.
Положенная не туда, ссылка поставщику не видна — значит идемпотентности нет,
и повтор после обрыва связи будет **второй покупкой**.

**3. Позиция ровно одна.** Схема требует `minItems=1, maxItems=1`.

### Требования к ссылке

1..40 символов, уникальна в пределах кабинета. Повтор с тем же значением
возвращает первый результат и `statusCode: 2`, тело запроса при этом
игнорируется.

**Обрезать надо одинаково при покупке и при поиске.** Разойдутся на один
символ — заказ не найдётся, и после обрыва мы решим, что покупки не было.
Поэтому обрезание живёт в одной функции (`cut_reference`).

## Получение кодов

```
GET /orders?referenceId=…&unhide=true
```

**`unhide=true` обязателен.** Без него коды приходят замазанными — `****9012`,
— и отправка такого «кода» покупателю была бы отчётом о выдаче, которой не
было.

**Фильтр тоже обязателен:** `unhide` без `referenceId` отвергается HTTP 422.

**У запроса есть побочное действие:** поставщик помечает коды полученными и
запоминает время первой выдачи. Звать «просто посмотреть» из диагностики
нельзя — только на пути настоящей выдачи.

Форма ответа отличается от ответа на покупку: `data.page.items[].vouchers[].pin`.
В шаблоне это закрыто общим чтением `codes_from()`.

## Право `orders:write` — самое дорогое слово в настройках ключа

Дословно из кабинета: без него ключ **покупает, но кода не отдаёт**. Деньги
списаны, выдать нечего.

Права раздаются по разделам (`shop`, `product`, `orders`, `funds`,
`direct_topup`, `transaction`, `dashboard`), отдельно чтение и запись. Есть
ещё `spendLimit` — потолок трат по ключу.

Проверять **до** первой покупки.

## Белый список IP

Об этом нет ни слова ни в SDK, ни в OpenAPI — сказано только на экране выдачи
ключа.

Практическое следствие: если сервис живёт там, где адрес меняется при каждом
обновлении, **ключ перестаёт приниматься после выката**. Выглядит это как
«ключ сломался», а дело в адресе.

Лечится прокси с **постоянным** адресом: в белый список вписывается он, а не
сервер.

**Через прокси обязаны идти и рабочие вызовы, и диагностика.** Проба,
ходящая мимо прокси, показывает адрес, с которого поставщик нас не видит, —
и «ключ не работает» остаётся загадкой. В шаблоне прокси задаётся один раз
при создании клиента.

Ключей два вида: временный на 48 часов и постоянный; белый список нужен
постоянному. По виду ключ не проверяется — в примерах документации
`sk_live_…`, а кабинет выдал `wli-…`, и проверка формы отвергла бы настоящий
ключ.

## Лимиты запросов

Опубликованы: `GET /api/v1/rate-limits`, читаются без ключа.

| Вызов | В минуту |
|---|---|
| `GET /services` — каталог целиком | **2** |
| `GET /orders` | 2 |
| `GET /orders` с фильтром | 20 |
| `GET /orders` с `unhide=true` | 5 (отдельный счётчик) |
| `POST /orders` — покупка | 120 |
| `GET /services/{id}/items/{id}` — один номинал | 120 |

Отсюда два правила шаблона:

**Каталог кешируется.** Он отдаётся одним ответом на 1263 услуги; два
оплаченных заказа подряд означали бы два тяжёлых чтения по 90 секунд
таймаута, и всё это время опрос заказов стоял бы.

**Перед покупкой читается один номинал, а не каталог.** 120 против 2 — это
разница между «можно под каждую покупку» и «нельзя».

## Повтор на 429

Повтор на «слишком часто» стоит места **в том же лимите**, из-за которого
отказ и пришёл. Три попытки подряд укладываются в то же окно, получают тот же
отказ и выедают остаток, который достался бы следующему экрану.

Поэтому: повтор **один**, и только если названную поставщиком паузу
(`Retry-After`) можно выдержать целиком. Спать 10 секунд из назначенных
шестидесяти значит гарантированно постучаться в ту же стену.

## Деньги и каталог

* **Баланс не в USDT.** Живой `GET /accounts` отдал три счёта: `USD`, `RUB`,
  `EUR`. Цены каталога тоже в USD.
* **Каталог:** `GET /services` — 1263 услуги одним ответом, у каждой
  вложенные `items[]` — номиналы с `id`, `price`, `currency`, `inStock`, а
  также `isLongOrder` и `minQtyToLongOrder`.
* **Roblox — только кодами.** 26 услуг, все типа `voucher`, `fields: null`:
  ник покупателя не требуется, выдаётся код. Прямого пополнения аккаунта у
  поставщика **нет**. Если товар описан как «Robux на аккаунт», описание
  неверно.
* Глобальные коды заметно выгоднее российских: 0.0099 USD за Robux на
  номинале 10000 против 0.0139–0.0156 у любого RU.

## Замена поставщика

Движку нужен протокол из трёх методов (`supplier.py`, класс `Supplier`):

```python
def item(service_id, item_id) -> dict          # цена и остаток номинала
def place(denomination_id, reference, qty) -> dict
def by_reference(reference) -> dict
```

Всё остальное — детали конкретного поставщика. Тесты движка гоняют
поддельного, так что подменить его можно, не трогая ни строчки выдачи.
