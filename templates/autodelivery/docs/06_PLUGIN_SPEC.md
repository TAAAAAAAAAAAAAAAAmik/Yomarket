# Плагины автовыдачи: полная спецификация

Всё, что есть в живом боте, — экраны, кнопки, настройки, поля, состояния,
команды. Снято с работающего кода, а не описано по замыслу.

Задача документа: чтобы плагин на новой площадке получился **таким же**, а не
похожим. Похожий разойдётся на первой же правке.

Снимок сделан 15.09 с версии бота `2026-09-15-dot-clears`. Каждое число
здесь — из кода, а не из памяти: 13 карт, 10 полей настроек, 11 состояний
журнала, `adjust(2, 2, 2, 1)`, обрезка журнала на 40 записях, таймаут 30 с,
срок жизни каталога 120 с. Сверять с кодом — по этим числам.

---

# Часть 1. Из чего состоит система

Три слоя, и они не знают друг о друге:

```
РЕЕСТР ТОВАРОВ        13 карт: что это, как узнать заказ, как активировать
       ↓
ДВИЖОК ВЫДАЧИ        покупка → ожидание кода → отправка → отметка
       ↓
КАБИНЕТ ПОСТАВЩИКА   ключ, прокси, каталог, баланс
```

Площадка (Юмаркет / PlayerOK) входит только в средний слой и только через
порт из пяти методов. Реестр и кабинет поставщика от площадки **не зависят
вовсе** — переносятся как есть.

# Часть 2. Реестр товаров

## 2.1. Что описывает одну карту

```python
@dataclass(frozen=True)
class GiftCard:
    slug: str              # "apple" — ключ настроек и адресов кнопок
    title: str             # "Apple" — как называется на экране
    emoji: str             # "🍎"
    subcategory: str       # ТОЧНОЕ имя подкатегории у поставщика
    unit: Unit             # MONEY / UNITS("робуксов") / PERIOD
    words: tuple[str, ...] # по каким словам узнаём заказ
    activation: str        # что написать покупателю вместе с кодом
    ad_title: str = ""     # заготовка названия товара
    ad_text: str = ""      # заготовка описания
    name_must_have: str = ""      # уточнение услуги словом
    name_must_not_have: str = ""
    autopick: tuple[str, ...] = ()  # слова для подстановки раздела витрины
    measured: str = ""     # дата замера на живом каталоге
    pitch: str = ""        # одна строка про товар для экрана
```

## 2.2. Главное правило реестра: выбор по подкатегории, а не по слову

`subcategory` — **точное** имя подкатегории у поставщика.

Почему это критично. На живом каталоге слово «xbox» находит **47 услуг**, а
гифт-карт среди них **16**. Остальное — подписки Game Pass, ключи отдельных
игр, аккаунты и `Roblox Wallet Code | XBox`, то есть **товар чужого
плагина**. Подбор по слову увёл бы его, и покупатель получил бы код Roblox
вместо карты Xbox.

Отбор услуги:

```python
def matches_service(self, service: dict) -> bool:
    if str(service.get("subcategoryName") or "") != self.subcategory:
        return False
    low = str(service.get("name") or "").lower()
    if self.name_must_have and self.name_must_have.lower() not in low:
        return False
    if self.name_must_not_have and self.name_must_not_have.lower() in low:
        return False
    return True
```

`name_must_have` / `name_must_not_have` нужны, когда одна подкатегория даёт
два плагина — например, Nintendo: карты и подписки.

| `xbox` | Xbox | MONEY | Xbox Gift Cards | 20.08 |
| `steam` | Steam | MONEY | Steam Wallet Gift Cards | 20.08 |
| `amazon` | Amazon | MONEY | Amazon Gift Cards | 20.08 |

| `airbnb` | Airbnb | MONEY | Airbnb Gift Card | — |
| `eneba` | Eneba | MONEY | Eneba Gift Card | — |
| `twitch` | Twitch | MONEY | Twitch Gift Card | — |

| `ozon` | OZON.ru | MONEY | OZON.ru Gift Card | — |

Семь семейств из тринадцати меряны на живом каталоге, шесть — нет, и на
экране карты это видно. Прочерк не значит «не работает»: он значит «разбор
номиналов здесь не проверяли», и продавцу лучше прогнать `🧪 Сухой прогон`
до включения.

**Единицы три:** `MONEY` (номинал — деньги: «10$»), `UNITS(имя)` (штуки:
«1000 робуксов»), `PERIOD` (срок подписки). От единицы зависит, как
разбирается номинал из названия товара и как он показывается.

**Robux — единственная карта с `UNITS`.** И у неё же особая история: раздел
жил отдельным плагином `auto_roblox` и переехал на общий движок. Перенос
настроек делает `_take_over_robux`, и самое важное в нём — список
`delivered`: потерять его значит выдать те же заказы заново, то есть купить
второй код за деньги продавца.

## 2.4. Поле `pitch` — про товар, а не про доходы

Одна строка на экране карты. Пишется **про товар**:

> «Пополняет Apple ID: App Store, iCloud, подписки. Логин покупателя не
> нужен — код он вводит сам.»

А не «самый ходовой номинал» и «покупают чаще всего»: это проверить нельзя,
а «код пополняет Apple ID» покупатель проверит сам.

## 2.5. Поле `measured` — честность про разбор номиналов

Дата замера на живом каталоге — или пусто, если семейство брали по
записанной таблице, не померив разбор.

Разница видна продавцу на экране карты: **«мерено»** значит, что все названия
семейства разобрались, а не «похоже, что разберутся».

## 3.2. Раскладка кнопок карты

```python
builder.adjust(2, 2, 2, 1)
```

Два в ряд: включить+настройки · выдать вручную+журнал · наличие+создать
товар · назад отдельной строкой. Та же раскладка у экрана настроек: регион+
слово · автоответ+заметка · название+описание · назад.

## 3.3. Почему «🏷 Создать товар» стоит на экране карты

Витрина и каталог обязаны сойтись. Объявление на номинал, которого у
поставщика нет, автовыдаче недоступно — а узнал бы об этом продавец из
отказа, когда покупатель уже заплатил.

Поэтому создание товара живёт **рядом с картой**, а не в общем разделе
объявлений: оттуда видно наличие.

## 3.4. Кнопки, которых нет намеренно

| Нет | Почему |
|---|---|
| «Проверить ключ» без заданного ключа | кнопка, которая заведомо не сработает, — то же обещание невозможного, что и совет ответить в закрытый чат. Появляется только после ввода ключа |
| «Купить код на пробу» | сухого прогона для магазинных заказов у поставщика **не существует**; `checkOnly` разрешён только для прямых пополнений |
| «Прислать код ещё раз» | второй вызов положил бы ту же покупку дважды |

# Часть 4. Все настройки

## 4.1. Настройки одной карты

Живут в `settings["plugins"]["gift_cards"][slug]`. Заводятся лениво,
умолчания **копируются** (`copy.deepcopy`) — общий список на все карты
означал бы, что журнал Apple пополняется выдачами Xbox.

| Поле | Тип | По умолчанию | Что делает |
|---|---|---|---|
| `enabled` | bool | **False** | включена ли автовыдача этой карты |
| `region` | str | `""` | регион кода: две буквы (US, TR, AE). Пусто — брать из описания товара |
| `keyword` | str | `""` | своё слово для узнавания заказа. Пусто — узнавать по обычным написаниям |
| `greeting` | str | `""` | автоответ покупателю **до** кода. Пусто — молчим |
| `note` | str | `""` | заметка, уходит покупателю **вместе** с кодом |
| `ad_title` | str | `""` | заготовка названия товара |
| `ad_text` | str | `""` | заготовка описания товара |
| `delivered` | list | `[]` | номера заказов, по которым код ушёл |
| `log` | list | `[]` | журнал выдач, новые в начале |
| `force` | list | `[]` | ручная очередь: выдать эти заказы |

## 4.2. Что написано на экране каждой настройки

Тексты подсказок — не украшение: каждая написана после того, как продавец
понял настройку неправильно.

### 🌐 Регион

> Введи регион кода — две буквы, как у поставщика (US, TR, AE…).
> Можно оставить пустым: тогда бот возьмёт регион из описания товара, где
> сам его и пишет.

### 🔤 Слово-опознаватель

Название «слово-опознаватель» продавцы понимают по-разному: одни думают, что
это слово для покупателя, другие — что бот будет искать его в описании.
Поэтому объяснение начинается с того, **где бот смотрит**, и показывает
пример на их же товаре:

> Бот смотрит на **название объявления на витрине** и решает, этой ли карте
> отдать заказ.
>
> Например, слово `эпл`:
>    ✅ «Эпл гифт карта 10$» — заберёт
>    ❌ «Apple Gift Card 10$» — пропустит, слова нет
>
> Пока слово не задано, бот узнаёт заказ по обычным написаниям названия
> карты. Задавать своё стоит, только если у тебя есть другие товары с тем же
> словом — скажем, аккаунты, — и они попадают в выдачу по ошибке.
>
> Точка «.» очистит настройку.

### 💬 Автоответ

> Уходит в чат заказа сразу, как заказ взят в работу — **до кода**.
>
> Нужен не всегда: обычно код приходит через секунды, и «принял заказ»
> следом за ним выглядит лишним. Но у долгих номиналов поставщик отвечает
> «принято, код будет позже», и ожидание тянется минутами — вот там молчание
> похоже на поломку.
>
> Точка «.» очистит — тогда бот молчит до самого кода.

### 📝 Заметка

> Введи заметку — она уйдёт покупателю вместе с кодом.

### 🏷 Название товара / 📄 Описание товара

Подстановки: `{номинал}`, `{регион}`, `{цена}`, `{карта}`.

У описания дополнительно:

> ⚠️ Ссылки панель не принимает — отказ придёт на последнем шаге мастера.

**Точка «.» очищает настройку** — общее соглашение для всех текстовых полей.

## 4.3. Настройки кабинета поставщика

Живут в отдельном хранилище `approute_creds`, **по аккаунту продавца**
(ключ `{uid}::{имя аккаунта}`).

| Поле | Обязательно | По умолчанию | Шифруется |
|---|---|---|---|
| `api_key` | **да** | — | **да** |
| `region` | нет | `"io"` | нет |
| `proxy` | нет | `""` | **да** |

**Регион не входит в обязательные** (`ar_fields()` возвращает только
`api_key`): у него есть значение по умолчанию, и требовать его выбора значит
держать продавца перед экраном, который и так знает ответ.

Два кабинета:

| Код | Кнопка | Что это |
|---|---|---|
| `io` | 🌍 approute.io | международный кабинет |
| `ru` | 🇷🇺 approute.ru | российский кабинет |

## 4.4. Шифрование секретов

```python
_AR_SECRET_FIELDS = ("api_key", "proxy")
```

Шифруются **на записи и только один раз**: `_seal(_unseal(value))` — без
`_unseal` внутри получился бы второй слой поверх первого.

Файл при хранении в файлах получает права `0600`.

Прокси **показывается только хостом и портом** — логин и пароль в строке
есть, но на экран не выходят никогда.

## 4.5. Как продавец вводит ключ: разбор свободного текста

Продавец копирует ключ из кабинета или из письма как придётся. Поэтому
`parse_creds` понимает синонимы:

| Поле | Как может быть названо |
|---|---|
| `api_key` | `api_key`, `apikey`, `key`, `x-api-key`, `ключ`, `апиключ`, `api-key`, `token`, `токен` |
| `region` | `region`, `регион`, `кабинет`, `домен` |
| `proxy` | `proxy`, `прокси`, `proxy_url` |

**По виду ключ не проверяется.** В документации поставщика примеры
`sk_live_…`, а кабинет выдал `wli-…` — проверка формы отвергла бы настоящий
ключ.

# Часть 5. Настройки Robux отдельно

Robux — та же карта общего движка, но у раздела остался свой экран с двумя
регионами:

| Код | Подпись |
|---|---|
| `GL` | 🌍 глобальный — подходит большинству аккаунтов |
| `RU` | 🇷🇺 российский — только для аккаунтов с регионом RU |

**Глобальные коды заметно выгоднее российских:** 0.0099 USD за Robux на
номинале 10000 против 0.0139–0.0156 у любого RU. Разница почти в полтора
раза — это не мелочь настройки, а выбор закупочной цены.

**Прямого пополнения аккаунта для Roblox у поставщика нет.** 26 услуг, все
типа `voucher`, у всех `fields: null`: ник покупателя не требуется, выдаётся
код. Если товар описан как «Robux на аккаунт», описание неверно.

# Часть 6. Что происходит при заказе — по шагам

## 6.1. Разбор заказа

```
новый оплаченный заказ
   ↓
кому он достанется   (по словам названия или по своему слову продавца)
   ↓ ПЕРВАЯ признавшая карта забирает — дальше цикл прерывается
оплачен ли           (статус; «создан» деньгами не является)
   ↓
не выдавали ли уже   (delivered)
   ↓
нет ли записи в журнале   (была — продолжаем ЕЁ, не заводим вторую)
   ↓
регион               (описание товара → настройка плагина)
   ↓
номинал              (число из названия → точное совпадение в каталоге)
   ↓
ЗАПИСЬ НАМЕРЕНИЯ в журнал + СОХРАНИТЬ
   ↓
приветствие покупателю (если задано, ровно один раз за заказ)
   ↓
перечитать номинал   (замена сухому прогону)
   ↓
ПОКУПКА              (постоянная ссылка referenceId)
   ↓
ожидание кода        (если IN_PROGRESS)
   ↓
КОД в запись + СОХРАНИТЬ
   ↓
отправка покупателю
   ↓
ОТМЕТКА «выдан» + СОХРАНИТЬ
```

## 6.2. Состояния записи журнала

Подбирают оборванную выдачу ДВА разных места, и путать их дорого:

* **возобновление** (`_gift_resume`) — отдельный проход, который чинит
  выдачи, оборванные посередине: выкат, перезапуск, упавшая задача. Статус
  заказа после обрыва больше не меняется никогда, значит обычный разбор по
  нему уже не сработает;
* **обычный проход по заказам** — видит заказ, пока он оплачен и его номера
  нет в `delivered`. Он берёт СУЩЕСТВУЮЩУЮ запись журнала и её ссылку
  покупки, а не заводит вторую: ссылка и есть вся защита от второго
  списания.

| Состояние | Что произошло | Возобновление | Обычный проход |
|---|---|---|---|
| `собираемся покупать` | запись есть, поставщика не звали | да | да |
| `покупаем` | вызов ушёл, ответа нет | да, **той же ссылкой** | да, той же ссылкой |
| `куплен, ждём код` | принято, кода нет | да, опросом | да, опросом |
| `куплен, отправляем` | код есть | да | да, отправит |
| `куплен, отправить не смогли` | чат не принял купленный код | **нет** | да, отправит снова |
| `номинал не перечитан` | сорвалась проверка перед покупкой | **нет** | да, с начала |
| `нет в наличии` | кончился к моменту покупки | нет | да, с начала |
| `поставщик отказал` | отказ с причиной | нет | да, той же ссылкой |
| `ответ без кода` | купили, кода нет | нет | да, но ссылка та же — второй раз не спишет |
| `не выдан` | отказ до покупки, с причиной | нет | да, с начала |
| `выдан` | покупатель получил | нет | нет: номер лежит в `delivered` |

**Возобновление берёт ровно четыре состояния** — верхние четыре таблицы
(в живом боте это кортеж `_GIFT_UNFINISHED`). Остальные для него — отказы:
они уже объяснены продавцу, и чинить их вслепую фоновым проходом значит
покупать второй раз то, что поставщик закончил.

**`куплен, отправить не смогли` — самое опасное из них.** Код КУПЛЕН, деньги
списаны, а покупателю он не ушёл. Бот показывает код продавцу прямо в
уведомлении и говорит передать руками: второй раз он покупать не станет.
Возобновление сюда не заходит намеренно — чат не принял сообщение по
причине, которая сама не проходит (закрытый заказ, блокировка), и повтор
раз в минуту превратился бы в бесконечную рассылку отказов.

# Часть 7. Команды диагностики

**Граница проходит не по слову «debug», а по тому, ЧЬЁ устройство команда
показывает.** Кабинет поставщика принадлежит продавцу — он его и чинит,
значит эти команды его. Устройство самого бота (выкат, хранилище, разбор
чужих ответов) продавцу не показывают: он купил подписку на сервис, а не
экскурсию по серверу.

**Продавцу — восемь команд:**

| Команда | Что показывает |
|---|---|
| `/apr_login` | ввод ключа свободным текстом |
| `/apr_forget` | удалить ключ |
| `/apr_balance` | баланс по всем счетам кабинета |
| `/apr_stock <слово>` | каталог: serviceId, itemId, цена за номинал, поля заказа |
| `/apr_item <serviceId> <itemId>` | цена, остаток и `isLongOrder` одного номинала — **тем же путём**, каким их читает выдача перед покупкой |
| `/apr_whoami` | каким IP нас видит поставщик |
| `/apr_debug` | сырой ответ по обоим кабинетам: статус, поля тела, `statusMessage`, `traceId` |

**Владельцу — одна, и она СКРЫТА:**

| Команда | Что показывает |
|---|---|
| `/apr_order_probe` | какую форму тела принимает покупка — на **несуществующем** товаре, денег не тратит |

Скрыта она потому, что показывает устройство НАШЕГО запроса, а не кабинет
продавца: форму тела `POST /orders` выясняли мы, и чинит её разработчик.

**Скрыто значит скрыто.** На скрытую команду бот отвечает продавцу ровно то
же, что на несуществующую: «только для администратора» рассказывало бы о
существовании скрытой части. И ни один экран не должен СОВЕТОВАТЬ набрать
скрытую команду — совет невозможного. Если подсказка нужна, она идёт
отдельным путём, видимым только владельцу.

**`/apr_debug` печатает значения, а не имена полей.** Первая версия
напечатала «поля тела: data, errorCode, …» и на этом остановилась, а ответ на
вопрос «что не так» лежал в значении `statusMessage`. Перечень имён без
значений отвечает «форма не та» и молчит о причине.

**`/apr_item` заменила «сухой прогон».** Его для магазинных заказов не
существует, и команда честно называется тем, что делает: читает один номинал
тем же вызовом, что и выдача.

# Часть 8. Ограничения, о которых надо знать заранее

## 8.1. Лимиты запросов поставщика

| Вызов | В минуту | Следствие |
|---|---|---|
| `GET /services` — каталог целиком | **2** | обязателен кеш |
| `GET /orders` | 2 | — |
| `GET /orders` с фильтром | 20 | — |
| `GET /orders` с `unhide=true` | 5 | **отдельный счётчик** |
| `POST /orders` — покупка | 120 | покупок хватит |
| `GET /services/{id}/items/{id}` | 120 | можно под каждую покупку |

Каталог — 1263 услуги одним ответом, и два лимита в минуту кончаются на
втором оплаченном заказе подряд. Поэтому в живом боте он **кеширован на
кабинет** (ключ кеша — хеш API-ключа плюс адрес шлюза, сам ключ в память не
кладётся: кеш попадает в диагностику), со сроком жизни 120 секунд и замком
на кабинет — два экрана, нажатых подряд, иначе выберут лимит сами себе.

Три вещи в этом кеше не для красоты:

* **возраст отдаётся наружу.** Показать вчерашние остатки, не сказав об
  этом, — ровно тот бодрый отчёт, от которого здесь уходят;
* **при отказе отдаётся просроченный каталог**, если он есть: список
  двухминутной давности полезнее пустого экрана;
* **покупка всё равно перечитывает свой номинал** отдельным запросом
  (`GET /services/{id}/items/{id}`, 120 в минуту) — на нём кеша нет, и
  цена с остатком берутся свежими.

Таймаут запроса к поставщику — 30 секунд, и он занимает поток: замок у него
общий с опросом чатов, так что письмо покупателя всё это время лежит.

## 8.2. Право `orders:write`

Дословно из кабинета: без него ключ **покупает, но кода не отдаёт**. Деньги
списаны, выдать нечего.

Права раздаются по разделам: `shop`, `product`, `orders`, `funds`,
`direct_topup`, `transaction`, `dashboard` — отдельно чтение и запись. Есть
ещё `spendLimit` — потолок трат по ключу.

## 8.3. Белый список IP

Об этом нет ни слова ни в SDK, ни в OpenAPI — сказано только на экране выдачи
ключа.

Ключей два вида: **временный на 48 часов** и **постоянный**; белый список
нужен постоянному.

Если сервис живёт там, где адрес меняется при каждом обновлении, ключ
перестаёт приниматься после выката. Выглядит как «ключ сломался».

**Лечится прокси с постоянным адресом** — в белый список вписывается он, а не
сервер. Кнопка «🧪 Годится ли он» **проверяет**: спрашивает адрес трижды и
сверяет с прямым — ловит и ротацию, и не применившийся прокси.

**Через прокси обязаны идти и рабочие вызовы, и диагностика.** Проба,
ходящая мимо, показывает адрес, с которого поставщик нас не видит.

## 8.4. Баланс

Живой `GET /accounts` отдал три счёта: **USD, RUB, EUR**. USDT среди них нет,
цены каталога тоже в USD.

Сравнивая закупку с другим поставщиком, сравнивать надо **деньги, а не
числа**.

# Часть 9. Что менять под PlayerOK

## 9.1. Переносится без правок

* реестр из 13 карт целиком (`subcategory`, `words`, `activation`, шаблоны);
* клиент поставщика: конверт, коды, покупка, получение кодов, прокси;
* подбор номинала и региона;
* движок выдачи со всеми состояниями;
* хранилище настроек и журнал;
* все экраны настроек карты — они про товар, не про площадку;
* экран кабинета поставщика целиком;
* все команды `/apr_*`.

## 9.2. Пишется заново

**Только адаптер площадки** — пять методов
(`templates/autodelivery/code/marketplace.py`):

```python
async def paid_orders() -> list[Order]
async def get_order(order_id) -> Order | None
async def send_message(chat_id, text) -> (bool, str)
def is_paid(status) -> bool
def order_url(order_id) -> str
```

Девять вопросов до первой строчки — в докстринге заглушки. Критичных три:
какие статусы означают оплату; где номер чата; где описание товара.

## 9.3. Что обязательно поменять в настройках

| Что | Почему |
|---|---|
| **Префикс ссылки покупки** | `referenceId` уникален в пределах кабинета поставщика, а кабинет один на все площадки. Совпадут префиксы — заказ №100 на Юмаркете и №100 на PlayerOK получат одну ссылку, и второй вернёт чужой код |
| Отдельное хранилище настроек | у площадок свои `delivered` и свои журналы |
| Тексты `activation` | если формулировка ссылается на площадку |

**Префикс — самое важное в этом списке.** Ошибка здесь даёт не отказ, а
молча выданный чужой код.

## 9.4. Что проверить до первой живой покупки

Полный чек-лист — `05_CHECKLIST.md`. Три пункта, которые чаще всего забывают:

1. право `orders:write` на ключе;
2. префикс ссылки отличается от того, что используется на другой площадке;
3. `is_paid()` проверен на **живом** заказе, а не по документации.

# Часть 10. Правила, по которым это написано

Не стиль, а причины прошлых поломок. Переносить вместе с кодом.

| Правило | Что случалось без него |
|---|---|
| **Первая признавшая карта забирает заказ** | «Apple или Xbox» признали обе — куплено два кода на один заказ |
| **Выбор услуги по подкатегории, не по слову** | слово «xbox» находит 47 услуг, карт среди них 16; остальное — чужой товар |
| **Ссылка покупки постоянна** | повтор после обрыва = вторая покупка |
| **Намерение записывается до вызова** | обрыв оставлял покупку без следа |
| **Код записывается до отправки** | закрытый чат — и купленный код ничей |
| **«Выдан» отмечается после отправки** | отчёт о выдаче, которой покупатель не видел |
| **Умолчания копируются на карту** | журнал Apple пополнялся выдачами Xbox |
| **Номинал только точный** | «похожий» — это недодать или переплатить за продавца |
| **Регион из описания важнее настройки** | у продавца товары разных регионов |
| **Плагин выключен по умолчанию** | он тратит деньги продавца у поставщика |
| **Каждый отказ доходит до продавца** | покупатель ждёт оплаченный заказ, продавец не знает |
| **Код ошибки переводится** | `FORBIDDEN` на экране — это «разбирайся сам» |
| **`traceId` печатается** | без него разбор превращается в переписку |
| **Точка очищает текстовое поле** | пустое сообщение Telegram отправить не даёт, и очистить настройку было нечем вовсе |
| **Экран обещает то, что код делает** | подсказка обещала очистку точкой, а общий обработчик клал точку текстом: `keyword` из одной точки перестаёт узнавать свою карту и забирает чужие заказы |
