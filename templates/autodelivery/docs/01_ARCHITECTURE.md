# Устройство конвейера

## Три входа, один путь

```
новый оплаченный заказ ─┐
ручная выдача кнопкой  ─┼──> deliver() ──> _finish() ──> купить → отправить
возобновление после    ─┘                               → отметить выданным
обрыва
```

**Путь к деньгам один намеренно.** Второй пришлось бы снабдить тем же
порядком записей, и однажды он бы с ним разъехался — молча, на настоящих
деньгах. Ручная выдача в живом боте ходит ровно тем же кодом, что и
автоматическая.

---

## Состояния записи

Каждая выдача — запись в журнале. Состояние записи и есть вся память системы.

| Состояние | Что произошло | Что делает возобновление |
|---|---|---|
| `собираемся покупать` | запись создана, поставщика ещё не звали | перечитает номинал и купит |
| `покупаем` | вызов ушёл, ответа нет | повторит **той же ссылкой** |
| `куплен, ждём код` | поставщик принял (`IN_PROGRESS`), кода нет | опросит по ссылке |
| `куплен, отправляем` | код есть, отправка идёт | отправит |
| `куплен, отправить не смогли` | код есть, чат не принял | попробует отправить снова |
| `выдан` | покупатель получил | ничего, запись закрыта |

Незавершённые: всё, кроме `выдан`. Их подбирает `resume_unfinished()` на
каждом проходе.

**Почему `куплен, отправить не смогли` считается незавершённым.** Код уже
оплачен. Бросить его значит выбросить деньги продавца и оставить покупателя
без товара по оплаченному заказу.

---

## Порядок записей

Это главное в шаблоне. Каждое сохранение стоит на своём месте по причине,
и каждая причина — из живого случая.

```
1. НАМЕРЕНИЕ  → в журнал, СОХРАНИТЬ
                    │
                    │  ← обрыв здесь: возобновление найдёт запись и купит
                    ▼
2. ПОКУПКА    → вызов поставщика с постоянной ссылкой
                    │
                    │  ← обрыв здесь: поставщик узнает ссылку и вернёт
                    │     прежний результат вместо второй покупки
                    ▼
3. КОД        → в запись, СОХРАНИТЬ
                    │
                    │  ← обрыв здесь: код не потерян, отправим следующим
                    │     проходом
                    ▼
4. ОТПРАВКА   → сообщение покупателю
                    │
                    ▼
5. ВЫДАНО     → в список выданных, СОХРАНИТЬ
```

**Намерение до покупки.** Иначе обрыв связи оставляет покупку без следа, и
повторить её нечем, кроме как вслепую — то есть купить второй раз.

**Код до отправки.** Чат может быть закрыт. Купленный код не должен остаться
никому.

**«Выдано» после отправки.** Отметка по факту покупки однажды доложила бы о
выдаче, которой покупатель не видел.

## Защита от второго списания — четыре рубежа

Самая дорогая поломка в такой системе — заплатить дважды за один заказ.
Рубежей четыре, и они независимы.

### 1. Список выданных
`delivered` хранит номера заказов, по которым код ушёл. Проверяется первым.

### 2. Запись в журнале
Заказ уже в журнале — значит вызов поставщика **мог уйти**. Повторять можно
только той же ссылкой, а заводить вторую запись нельзя: по ней потом не
понять, что покупали.

### 3. Постоянная ссылка покупки
`order_reference(prefix, card, order_id)` считается **только из номера заказа
и вида товара**. Ни времени, ни случайных чисел. Поставщик узнаёт её и
отвечает `IDEMPOTENCY_REPLAY` — «такой заказ уже был, отдаю прежний
результат» — вместо новой покупки.

Это последний рубеж: он работает даже когда запись журнала вытеснена по
длине. На него стоит отдельный тест.

### 4. Первая признавшая карта забирает заказ
Товар «Apple или Xbox» признали бы оба вида. Без остановки на первом бот
купил бы два кода на один оплаченный заказ.

## Ожидание кода

Поставщик законно отвечает «принял, кода пока нет». Ждём — но не бесконечно:

```python
POLL_STEPS   = (12, 12, 15, 20, 30, 30, 30, 45, 60, 60)
POLL_CEILING = 120.0
```

**Почему потолок жёсткий.** Ожидание занимает поток, а на нём стоит опрос
заказов. Письмо покупателя лежало бы всё это время. Незаконченная запись при
этом не теряется: её подберёт возобновление следующим проходом.

**Терминальный статус без кода — это отказ, а не «ещё подождём».**
`PARTIALLY_COMPLETED` тоже терминальный. Провалиться отсюда в покупку значит
купить ещё раз то, что поставщик уже закончил.

## Перечитывание номинала перед покупкой

Сухого прогона покупки у поставщика **не существует**: `checkOnly` разрешён
только для прямых пополнений, а коды — это `voucher`.

Замена: перечитать один номинал прямо перед покупкой
(`GET /services/{id}/items/{id}`, 120 запросов в минуту против 2 у каталога).

Это ловит два случая:
* номинал кончился, пока заказ лежал в очереди — покупки не будет, денег не
  потратим;
* цена изменилась — записываем **до** покупки, иначе «почему списалось
  столько» объяснить будет нечем.

## Что движок делает при любой беде

Говорит продавцу причину. Всегда.

«Ничего не произошло» без причины — самая дорогая тишина в такой системе:
покупатель ждёт оплаченный заказ, продавец не знает, а заметит это через
час, когда откроется спор.

Поэтому у каждого отказа есть текст на русском, и он попадает и в журнал, и
в уведомление. Код ошибки поставщика переводится; `traceId` печатается — по
нему поставщик находит запрос у себя.

## Чего в движке нет

| Нет | Почему |
|---|---|
| Знания о площадке | всё за портом `Marketplace`; движок не знает, куда пишет |
| Знания о конкретном поставщике | за протоколом `Supplier`; тесты гоняют поддельный |
| Разбора собственного текста | решения принимаются по `Result` и полям записи, а не по фразам. Разбор своей же прозы ломается на первой правке формулировки |
| Тихих пропусков | любой отказ доходит до продавца |
