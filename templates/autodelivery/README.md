# Шаблон автовыдачи кодов

Рабочий каркас плагина «оплаченный заказ → код покупателю». Вынут из живого
бота, где он выдаёт 13 видов подарочных карт и Robux на маркетплейсе Юмаркет.

Задача шаблона — чтобы на новой площадке ты писал **только адаптер площадки**,
а не всю выдачу заново. Всё остальное здесь уже есть и покрыто тестами.

---

## Что в коробке

```
code/
  marketplace.py   порт площадки + ЗАГЛУШКА PlayerOK со списком вопросов
  supplier.py      клиент поставщика кодов AppRoute — переносится как есть
  catalog.py       номинал из названия, регион из описания, подбор у поставщика
  store.py         состояние выдачи, атомарная запись, журнал
  delivery.py      движок: покупка, ожидание кода, отправка, возобновление
tests/
  test_delivery.py 20 тестов на поддельных площадке и поставщике
docs/
  01_ARCHITECTURE.md   конвейер, состояния, инварианты
  02_MARKETPLACE_PORT.md что именно писать под PlayerOK
  03_SUPPLIER.md         всё про поставщика: конверт, коды, лимиты, права
  04_PITFALLS.md         грабли — каждая денежная
  05_CHECKLIST.md        чек-лист приёмки до первой живой покупки
  06_PLUGIN_SPEC.md      ВСЁ об экранах и настройках: реестр карт,
                         дерево кнопок, каждое поле, команды, лимиты
example_bot.py     минимальная сборка: как всё соединяется
```

Проверка, что каркас цел:

```bash
cd templates/autodelivery
python3 -m unittest discover tests -v      # 20 тестов, сети не требуют
```

## Граница честности

**Половина, зависящая от площадки, здесь не написана — и это осознанно.**

Что переносится **1:1**, проверено живыми вызовами:
* клиент поставщика AppRoute (конверт ответа, покупка, получение кодов);
* подбор номинала и региона;
* весь движок выдачи с защитой от двойного списания;
* хранилище и порядок записей;
* тесты.

Что **надо написать самому**, потому что API PlayerOK в этом шаблоне не
проверялся ни разу:
* адаптер площадки — класс с пятью методами (`code/marketplace.py`);
* способ узнавать о новых заказах (опрос или вебхук);
* интерфейс продавца: экран плагина, ключ поставщика, журнал выдач.

Догадки о чужом API стоили бы денег ровно там, где идёт покупка. Поэтому
вместо выдуманных полей в заглушке лежит **список из девяти вопросов**, на
которые надо ответить до первой строчки адаптера.

## План на день

Порядок не случайный: каждый шаг проверяем до того, как он сможет потратить
деньги.

### Час 1. Разведка API площадки

Открой `code/marketplace.py`, прочитай девять вопросов в докстринге
`PlayerokMarketplace` и ответь на них — руками, `curl`'ом, в консоли.
Записывай ответы прямо туда же комментариями.

Критичных три:
1. **какие статусы означают «оплачено»** — ошибка здесь = выдача бесплатно;
2. **где лежит номер чата** — почти наверняка не равен номеру заказа;
3. **где лежит описание товара** — из него читается регион кода.

### Час 2. Адаптер площадки

Реализуй пять методов. Ничего умного: привести ответ площадки к `Order` и
отправить сообщение. Логики выдачи здесь быть не должно — она вся в движке.

Готово, когда работает:

```python
orders = await market.paid_orders()
ok, why = await market.send_message(orders[0].chat_id, "проверка связи")
```

### Час 3. Ключ поставщика и каталог

Заведи ключ AppRoute с правом **`orders:write`** (см. `docs/03_SUPPLIER.md` —
без него ключ покупает, но кода не отдаёт). Проверь, каким адресом тебя видит
поставщик, и при необходимости поставь прокси с постоянным адресом.

Напиши `catalog_of(card, region)` — он отдаёт список номиналов из каталога
поставщика. Каталог кешируй: `GET /services` разрешён **2 раза в минуту**.

### Час 4. Сборка

Возьми `example_bot.py`, подставь свой адаптер. Прогони тесты — они должны
остаться зелёными: движок ты не трогал.

### Час 5. Проба на дешёвом номинале

Самый дешёвый номинал, свой тестовый заказ. Проверь по `docs/05_CHECKLIST.md`:
код пришёл, журнал заполнен, повторный проход **не покупает второй раз**.

### Час 6. Обрыв и возобновление

Убей процесс между покупкой и отправкой (или временно верни из
`send_message` ошибку). Подними заново. `resume_unfinished()` обязан
дослать код и **не купить второй раз**.

Это главная проверка дня: обрыв случается не от сбоя, а от обычного выката.

### Час 7. Интерфейс продавца

Экран плагина: включить/выключить, ключ поставщика, регион, слово-опознаватель,
журнал выдач, ручная выдача по номеру заказа.

**Не придумывай его заново — он уже описан.** `docs/06_PLUGIN_SPEC.md` — это
живой интерфейс Юмаркет-бота целиком: дерево экранов с каждой кнопкой и её
`callback_data`, все десять полей настроек с умолчаниями, текст каждой
подсказки дословно, раскладка кнопок, кнопки, которых нет НАМЕРЕННО, и
команды диагностики с границей «что показывать продавцу, а что нет».

Оттуда же — единственная правка, которую в настройках обязательно сделать
под другую площадку: **префикс ссылки покупки** (`docs/06_PLUGIN_SPEC.md`,
часть 9.3).

### Час 8. Запас

Уйдёт на то, что вылезет. Что-нибудь обязательно вылезет — скорее всего
пагинация заказов или статус, которого нет в твоём списке «оплачено».

## Чего в шаблоне намеренно нет

| Нет | Почему |
|---|---|
| Telegram-бота целиком | у тебя он уже есть; шаблон — про выдачу, а не про интерфейс |
| Базы данных | `JsonStore` заменяется на свою; движку важен только интерфейс |
| Второго поставщика | добавляется реализацией протокола `Supplier` |
| Готового адаптера PlayerOK | их API не проверялся — выдумывать поля дороже, чем написать самому |
| Сухого прогона покупки | для магазинных заказов его у поставщика **не существует**; замена — перечитать номинал перед покупкой, это уже в движке |

## Одно правило, если читать некогда

**Порядок записей важнее всего остального.**

```
намерение → СОХРАНИЛИ → покупка → код → СОХРАНИЛИ → отправка → выдано → СОХРАНИЛИ
```

Намерение до покупки — иначе обрыв оставит покупку без следа.
Код до отправки — иначе купленный код останется никому.
«Выдано» после отправки — иначе доложишь о выдаче, которой покупатель не видел.

Всё остальное в шаблоне — следствие этих трёх строк.
